# 皓量云擎云业务运营系统后端开发规范

## 适用范围

本文件适用于 `backend/` 及其所有子目录，并继承仓库根目录 `AGENTS.md`。子目录若存在更具体的 `AGENTS.md`，继续叠加执行。

## 技术栈与目录边界

- 使用 PHP 8.4、Webman、MySQL 8.0 和 Redis。
- `app/`：后端应用源码；核心业务采用模块化单体组织，不得为追求“可插拔”而把产品、订单、客户、财务、营销和履约等核心能力全部插件化。
- `app/modules/`：按业务能力划分的模块目录。安装、会员、产品注册、独立产品类型、报价、订单、支付、履约、财务、营销和渠道等能力分别收拢在自己的模块内。
- `app/shared/`：真正跨模块且语义稳定的公共能力；不得把特定业务规则或仅被单个模块使用的代码放入该目录。
- `app/controller/`、`app/command/`、`app/middleware/`、`app/exception/`、`app/process/` 和 `app/queue/`：仅保留全局 HTTP 入口、受控维护命令及跨模块运行时能力；模块专属代码必须放回对应模块。
- `plugins/<category>/<plugin_id>/`：本系统业务插件目录，按 `provider/payment/identity/sms/mail/storage/oauth/captcha/product/feature` 分类，由宿主注册器负责加载。当前供应插件位于 `plugins/provider/`，旧 `plugin/` 已移除；短信、邮件、支付、实名、存储、第三方登录和人机验证已提供固定 v1 契约。Webman 基础组件的 `config/plugin/` 和 Composer 依赖继续保留。
- `themes/`：官网与会员中心的统一主题包（website与console目录，整套选择）；官网使用Twig，会员中心交付普通SPA构建，静态资源发布到受控的公开目录。
- `public/`：唯一公开文件边界；配置、模板源码、私有上传、日志和迁移不得放入该目录。
- 禁止直接修改 `vendor/`、`runtime/` 及其他框架或工具生成内容。
- `public/admin/`、`public/console/` 与 `public/install-assets/app/` 是前端构建产物，必须由对应 Vite 应用生成；发行版需要提交这些产物，确保服务器无需 Node.js 即可运行。
- 安装器的 React、Arco Design React 与样式由 Vite 一并打包至 `public/install-assets/app/`；依赖版本及许可证必须随更新核验，不在运行时使用 CDN。

## 架构与依赖规则

后端采用“模块化单体 + 选择性 DDD”。目录首先按业务模块划分，再按实际复杂度决定模块内部是否需要领域层，不得为了形式完整而给每个模块机械创建空层或无业务意义的实体、仓储和领域服务。

```text
app/
├── modules/
│   └── <module>/
│       ├── controller/       模块 HTTP 入口、参数接收和响应转换
│       ├── application/      用例编排、事务边界和应用服务
│       ├── domain/           按需使用的实体、值对象、领域服务和领域事件
│       ├── contract/         Repository、Gateway 和外部能力接口
│       ├── infrastructure/   数据库、Redis、队列和第三方接口实现
│       ├── exception/        模块业务异常及异常映射
│       └── middleware/       仅作用于本模块的中间件
├── controller/               全局页面或跨模块 HTTP 入口
├── command/                  系统安装、迁移、维护等受控 CLI 入口
├── middleware/               全局横切中间件
├── exception/                全局异常与异常处理器
├── process/                  Webman 自定义进程
├── queue/                    跨模块队列运行入口
└── shared/                   跨模块且稳定的公共能力
```

- 简单配置、查询和普通 CRUD 可以使用 Controller、Application、Contract 与 Infrastructure 的精简结构；只有存在状态流转、不变量、复杂计算或多对象协作时才引入完整 Domain 模型。
- 产品销售配置、条件定价、订单状态、支付退款、账务、履约、上下游同步、优惠活动、返利和结算等核心复杂领域应使用实体、值对象、领域服务及领域事件保护业务规则。
- Controller 只负责 HTTP 边界，不直接访问 Model、数据库、Redis 或第三方接口，必须调用本模块的 Application 用例。
- Domain 不得依赖 `Request`、`Response`、`Db`、`Redis` 或其他 Webman/Illuminate 基础设施类，也不得依赖 Controller、Application 或 Infrastructure。
- Application 可以依赖本模块的 Domain 和 `contract/` 接口，不依赖 Infrastructure 具体实现；Infrastructure 实现 Contract 并通过容器完成绑定。
- 业务表的 Eloquent 模型统一放在所属模块 `infrastructure/model/`，使用 `Model` 后缀并继承 `support\Model`；显式声明无前缀逻辑表名、casts、fillable、hidden 和时间戳策略，不使用全局 `app/model/`。
- 跨层复杂数据优先使用明确的 DTO、值对象和接口；只读、局部且结构稳定的简单结果可以使用带精确 PHPDoc array shape 的数组。
- 跨模块业务协作和写入必须通过公开 Application 门面或 Contract，不访问对方 Model 或仓储实现。后台复杂联表展示查询允许在 Infrastructure 的专用只读查询实现中访问相关表；必须显式选择输出列，不得借此跨模块写入。
- 涉及支付成功、订单状态与履约调度等“数据库提交后必须可靠执行”的事件，必须评估事务 Outbox、幂等消费、重试和补偿，不能依赖内存事件保证可靠性。
- `shared/` 不能反向依赖具体业务模块；仅被一个模块使用的代码保留在该模块内部，避免形成万能公共层。
- 核心领域不得出现供应商专属字段；产品销售契约、连接器能力、履约字段与供应商参数通过版本化契约和映射规则衔接。
- 产品身份通过安装或前向迁移注册，云服务器固定为一个产品，销售方案只引用该身份，不再按方案创建或重命名产品；产品表不重复保存 product_type，固定定义使用 definition_key。订单、服务及插件能力中的业务标识和版本化处理器契约继续保留，不提供后台产品类型 CRUD。公共产品注册只承担固定标识、展示入口、发布索引等稳定能力；云服务器、物理服务器、域名和 SSL 证书等产品分别拥有自己的配置模型、组合校验、管理页面、购买页面和生命周期，不得用通用属性表、无约束 JSON 或单一万能产品实体替代类型领域。
- 云服务器的地域、可用区、线路、规格、镜像、系统盘、数据盘、带宽、IP、防护和初始化参数属于云服务器领域。供应商标识与字段保存在供应映射中；密码、私钥等敏感值使用短期凭证引用传递，不进入产品版本、报价快照、普通订单字段或日志。
- 可复用的线路、规格、镜像和存储类型通过专属关系表关联多个可用区，防护关联多条线路；保留可用区归属地域、规格归属规格组等明确层级。业务使用 `zone_ids/line_ids`，旧标量字段只作兼容。镜像最低 CPU、内存和系统盘要求必须同时在选项、完整配置和发布校验中执行。带宽阶梯明确区分累进与整段价格，使用整数分并随版本封存。
- 供应映射按连接、资源类型、本地标识及可用区作用域维护，指定作用域优先于默认对应。发布前逐部署位置调用插件契约校验，封存完整映射；CPU、内存、各块磁盘容量、带宽和 IP 数量通过标准配置传递，不能仅发送内部 ID，也不能用当前映射覆盖历史绑定。参数预览与真实生产能力分别标记。
- 销售配置发布为不可变版本；报价、订单、履约任务和服务实例保存创建时的类型契约、销售版本、标准化配置、供应绑定和政策快照。后续调价、同步供应目录或编辑商品不得静默改变历史交易和存量服务。
- 产品类型必须通过版本化 Contract 提供可选项解析、完整配置校验、类型计价和生产请求构建能力；公共报价、订单和履约模块不得通过判断类型字符串、读取类型内部表或堆积供应商条件分支实现类型差异。
- 社区版、专业版和企业版共用同一套领域代码，通过稳定的功能授权、能力声明和许可证策略控制，不维护三套长期分叉代码。
- 官网账号连接、商业许可证和应用购买权益分别校验。新增高级功能必须通过 `CommercialFeatureGateInterface` 按 capability、operation 和宿主核实的 context 检查签名权益及期限，再执行 RBAC 和对象归属检查；浏览器配置、连接成功或已下载商业包均不能授予商业能力。
- 官网集成统一使用 v1 实例签名协议。固定 HTTPS 地址、预置信任公钥、下载域名白名单及私有目录统一在 `config/official_platform.php` 配置，不使用 `OFFICIAL_PLATFORM_*` 环境变量；修改后完整 restart，在线更新不得覆盖此文件。安装私钥仅置于 Web 根目录外的持久私有卷，官网令牌和证书加密保存，不输出到浏览器或审计报文。
- 软件更新提醒由后端维护任务定时检查并验签后保存摘要，浏览器只读本机缓存。失败保留上次成功结果及时间；十分钟有效的签名清单不作为长期安装凭证，管理员确认及执行下载前必须重新获取、验签并核对批准的版本与摘要。
- 系统更新和应用安装由授权接口受理固定任务，再由专用维护进程执行。先核对签名、上下文、文件摘要及包路径，备份并进入维护状态，只调用受控前向迁移和完整重启命令；迁移阶段失败或文件状态未知时保留备份并停止自动重放。协议与部署说明见 `docs/development/official-platform-implementation.md`。
- 当前阶段保持单体部署和单一安装包；只有出现明确的独立扩缩容、独立数据边界或团队自治需求时，才评估将成熟模块拆分为服务。

## 消息与队列规范

- 通知通过 `MessagePublisherInterface` 显式调用，与业务默认数据库事务共同提交；任务表作为 Outbox，Redis 只传投递 ID。保存配置不得隐式发送，不用模型 Observer 发信。
- 队列同步确认后才更新补投租约；消费者数据库原子领取、固定请求标识与租约令牌，重复入队不得重复发送。队列前缀按安装实例隔离，同实例所有进程保持一致。
- 厂商受理、最终送达、站内可见和用户已读分别建模；发送结果未知或外部领取超时不得自动重发或切通道，明确失败才按权限和次数上限重试。
- 模板及收件地址快照加密保存；Redis、日志、审计及响应不得泄露收件地址、正文、验证码、Webhook 或原始厂商异常。认证收件箱只能读取本人记录，已读按接收对象独立保存。
- 普通通知入口拒绝验证码；验证码须独立有效期、单次消费与频率限制。新增事件要同时实现真实业务触发与事务/幂等测试，不能将目录条目当作已接入。
- 运行与验收说明见 `docs/development/message-runtime.md`。

## ORM 与事务规范

- 普通单表业务读写优先通过模型；复杂联表、聚合、批量处理及受控原子更新可以使用查询构建器。模型不是查询构建器的表名包装：普通新增使用 `create()`，实体修改使用白名单 `fill()`/`save()`，状态条件更新使用带条件的模型查询。
- 保留 Repository Contract；Controller、Application 和 Domain 不依赖 ORM 模型。仓储向上返回 DTO、领域对象或带明确 shape 的受控数组，禁止直接把模型完整 `toArray()` 当作 API 响应。
- 接口金额和标识保持整数，业务时间保持原有 `Y-m-d H:i:s` 字符串，空值保持 null。敏感哈希、密文、私有配置快照不能通过新增字段自动进入响应。隐藏字段只作纵深保护，不能替代查询列及输出白名单。
- 模块内关联按需定义并显式预加载；分页总数与列表使用同一过滤条件，不得在每行装饰过程中额外查询关联。
- 跨模块付款由订单 `PayOrderByWalletService` 持有 `TransactionManagerInterface` 事务，使用当前默认连接，锁顺序固定为订单、资金账户、来源批次、产品库存池与占用记录。模型及参与仓储不得自行切换连接。
- 资金门面只接收明确付款指令，不查询或修改订单表；充值匹配和来源扣减规则由资金应用层负责，仓储承担读取、锁定和持久化。
- 支付、扣款、通知及外部任务通过显式用例调用，禁止模型 Observer 隐式触发。`OutboxWriterInterface` 必须在业务事务内调用；写入待处理记录不代表已经投递或履约。
- 安装前探测、迁移、升级继续使用独立短生命周期 PDO，不依赖尚未就绪的业务 ORM。

## PHP 与 Webman 规范

- PHP 文件使用 `declare(strict_types=1);`，参数、属性和返回值必须声明类型。
- 类默认声明为 `final`；不可变数据优先使用 `readonly`。
- 所有新增或修改的 HTTP 接口必须使用已安装的 `webman/validation` 对路径、查询、请求体及上传文件等外部输入进行白名单验证；优先使用 `support\validation\Validator`，可复用规则放入对应业务模块的 `validation/`，并为创建、更新等不同语义使用明确场景或独立验证器。验证通过后仍须显式转换类型并执行权限、对象归属、数据库约束和领域业务规则，验证失败统一交由全局异常处理及 `ApiResponse` 返回 `data.errors`，不得在 Controller 中散落手写 `if` 校验或自定义错误响应。
- `app/` 下目录统一使用小写，多单词目录使用下划线；命名空间必须与目录一致。
- 遵循 PER Coding Style，保持单一职责和可测试性，避免无业务语义的超大 Service 或工具类。
- 代码必须有合理的换行、缩进和空行，统一使用 4 个空格缩进，不使用 Tab；每行只写一条语句，方法体、条件分支、循环和异常处理使用大括号并分行书写，禁止把完整方法、嵌套控制流程或多条语句挤在一行。较长的参数列表、数组、复合条件和链式调用按语义换行并保持一致缩进，不同逻辑步骤之间适当留空行；包含多步逻辑的闭包分行展开，简短的纯表达式箭头函数可保持单行。新增、修改代码及文档中的 PHP 示例均须遵守，不以减少行数牺牲可读性。
- Webman 是常驻内存、多进程应用，不得把请求、当前用户、Session、事务或租户状态保存在静态属性、单例或全局变量中。
- 常驻对象持有的连接、缓存和监听器必须明确生命周期，避免跨请求数据泄漏和重复注册。
- 配置、进程定义、Composer 依赖或启动期加载内容变更后，必须说明是否需要 reload/restart，不得假设热更新自动生效。

## 路由规范

- 全局必须在 `config/route.php` 调用 `Route::disableDefaultRoute()`，禁止依赖 Webman 的默认控制器路由暴露接口；使用 Attribute 路由的控制器仍须添加 `#[DisableDefaultRoute]`，形成控制器级防护。
- 新增核心业务 API 默认使用 Webman 2.2 的 PHP Attribute 路由，并通过 `#[RouteGroup]` 声明版本化前缀、通过 `#[Get]`、`#[Post]`、`#[Put]`、`#[Patch]` 或 `#[Delete]` 显式声明路径、请求方法及唯一名称。
- 禁止在业务接口中使用不带路径的 `#[Get]`、`#[Post]` 等 Attribute，禁止使用 `#[Any]` 代替明确的 HTTP 方法；兼容或兜底场景确需使用 `#[Any]` 时必须在代码注释和测试中说明原因。
- 核心 API 前缀固定为 `/api/admin/v1`、`/api/console/v1`、`/api/public/v1` 和 `/api/partner/v1`；`partner` 入口仅用于独立实例之间的上下游机器调用，在线安装接口保留 `/api/install` 作为安装期特例。当前未上线阶段，内部接口直接更新当前主版本，删除旧字段别名和无调用旧入口，同步所有调用方、契约和测试。正式发布且存在既有消费者后，破坏性接口变更才新增主版本前缀并安排迁移。
- 路径使用小写复数名词和短横线，禁止把控制器名、PHP 命名空间或内部实现细节暴露到 URL；普通 CRUD 使用 HTTP 方法表达语义，状态流转使用清晰的子资源或动作路径。
- 路由名称使用 `<入口>.<复数资源>.<动作>`，例如 `admin.products.index`、`console.orders.show`；名称发布后视为稳定契约，必须全局唯一，不得随意修改或复用为其他语义。
- 系统入口、官网与主题入口、在线安装器、SPA catch-all、健康检查、全局 fallback 和运行时动态分发继续集中定义在 `config/route.php`；普通业务 API 不得以闭包路由实现。
- 认证类中间件优先声明在控制器类上，限流或接口专属中间件可以声明在方法上；Attribute 中间件只负责 HTTP 横切能力，细粒度权限、对象归属和业务授权仍必须由 Application 或权限服务校验。
- 业务插件路由必须由宿主根据已审核清单和固定处理器注册，使用 `/api/<入口>/v1/plugins/<plugin_id>` 前缀；提供者及渠道插件优先通过核心固定用例和回调入口调用，不自行注册任意控制器。需要 Attribute 的扩展只允许扫描审核通过的类别和目录，并同步校验清单、权限及路由冲突；新 `plugins/` 不依赖 Webman 的 `plugin/` 自动扫描。启用、禁用、安装、升级或路由变更须使各 Worker 注册一致，自动加载器或启动绑定变更后完整 restart。运行时机制按插件优化方案建设，不把规划描述为已实现。
- Attribute 路由在 Worker 启动时扫描并注册；不得把数据库查询、网络请求、环境写入或其他有副作用的操作放入 Attribute 构造、控制器静态初始化或路由配置加载阶段。
- Controller 继续遵循 HTTP 边界职责，只接收和转换请求、调用 Application 用例并生成统一响应；使用 Attribute 路由不改变现有分层、异常处理和 `ApiResponse` 规范。
- 路由的详细设计、示例、迁移策略和验收清单见 `docs/development/backend-routing.md`。

## 复用与工具类规范

- 多处重复且语义稳定的通用操作可以封装为工具类或公共服务，避免复制粘贴；封装前应确认输入、输出、异常和副作用边界清晰，不能仅因代码片段看起来相似就过早抽象。
- 纯计算、格式转换、脱敏、编码等无状态逻辑可以放入职责单一的工具类；涉及数据库、Redis、文件、网络、日志、配置或时间等外部依赖的操作必须封装为可注入服务，并通过构造函数显式注入依赖。
- 业务规则不得迁入通用工具类。产品定价、订单状态、退款资格、权限判断和履约决策等规则应保留在对应 Domain 或 Application 层；数据库及第三方调用仍应遵循 Contract 与 Infrastructure 边界。
- 工具类放置位置必须服从作用域：仅供单个业务域使用的能力放在该领域内部；真正跨领域且稳定的能力才放入 `app/shared/`。不得创建无明确职责的 `CommonUtil`、`Utils`、`Helper` 或万能公共类。
- 工具类和公共服务必须使用表达业务含义的类名与方法名，保持小而专一；不得通过动态数组、全局变量或隐式上下文隐藏必要参数。
- 只有无状态、无副作用的纯函数或命名构造器可以使用静态方法；存在依赖或副作用的可复用操作必须使用实例方法和依赖注入，以便替换与测试。
- Webman 常驻进程中的工具类和公共服务不得缓存当前请求、用户、Session、租户、事务或其他请求级可变状态，避免跨请求数据泄漏。
- 新增可复用能力时应补充 PHPDoc 和针对输入边界、异常路径及副作用的单元测试；修改公共行为前必须搜索全部调用方并评估兼容性。

## 注释与 PHPDoc 规范

- 在类、接口、枚举、公共方法、受保护方法、复杂数据结构和关键业务规则上补充 PHPDoc，说明职责、输入输出、业务约束、副作用、异常及并发或常驻内存注意事项；私有方法存在复杂逻辑或非显然约束时也必须补充。
- PHPDoc 统一采用 PhpStorm 默认的完整标签式格式和标准 `/** ... */` 结构：首行写摘要；仅有摘要时，下一行直接书写标签，不得在摘要与标签之间保留空白注释行；确有详细描述时，摘要后空一行书写详细描述，再空一行书写标签。
- 已声明原生参数和返回类型的方法，PHPDoc 仍必须完整列出每个 `@param` 和 `@return`，不得以“与原生类型重复”为由省略；无返回值的方法使用 `@return void`，构造函数按照 PhpStorm 默认格式只列参数而不写 `@return`。
- 每个 `@param` 必须包含准确类型、变量名和参数业务含义；`@return` 必须包含准确类型，并在返回含义不直观时写明说明。同一注释块存在多个参数时，类型和变量名列按 PhpStorm 默认格式对齐。
- 方法可能主动抛出或透传调用方需要处理的异常时，必须使用 `@throws` 写明异常类及触发条件；不得记录实际上不会抛出的异常，也不得遗漏稳定公开 API 的异常契约。
- 根据实际需要准确使用 `@var`、`@template`、`@extends`、`@implements`、`@deprecated` 和 `@see` 等标签。
- 数组、集合、回调和泛型无法由原生类型完整表达时，必须使用 PHPDoc 标明 array shape、元素类型、键类型、回调签名或模板类型，不得只写含糊的 `array`、`mixed`。
- PHPDoc 不能替代 PHP 原生类型声明；参数、属性和返回值仍须使用尽可能精确的原生类型，文档负责补充业务语义和静态分析信息。
- 行内注释优先解释“为什么这样做”、兼容边界、事务或幂等策略和不直观的算法，不要逐行复述代码，也不要保留大段已注释掉的废弃代码。
- 注释必须与实现同步更新；无法确认、已经过期或可能误导维护者的注释应立即修正或删除。

标准示例：

```php
/**
 * 校验用户是否满足指定年龄要求。
 * @param string $name 用户名
 * @param int    $age  年龄
 * @return bool 是否满足要求
 * @throws InvalidArgumentException 年龄小于零时抛出
 */
```

存在详细描述时的示例：

```php
/**
 * 校验用户是否满足指定年龄要求。
 * 用户名会先去除首尾空白；年龄必须为非负整数。
 * @param string $name 用户名
 * @param int    $age  年龄
 * @return bool 是否满足要求
 * @throws InvalidArgumentException 年龄小于零时抛出
 */
```

## 插件规范

- 普通项目内模块放在 `app/modules/`；具备独立安装包、版本和生命周期的扩展统一使用 `plugins/<category>/<plugin_id>/`。配置、固定方法、边界及分阶段实施遵循 [业务插件体系优化方案](../docs/architecture/business-plugin-optimization.md)。系统尚未上线，当前协议统一为 v1（清单值 `1.0`）；全部供应插件使用公共 DTO 接口，宿主提供受限 HTTP 客户端及快捷方法，不维护旧数组入口或双版本兼容分支。
- 插件标识仅使用小写字母、数字和下划线，发布后不得随意修改。
- 插件包摘要覆盖运行文件及本地 SDK；普通 `.DS_Store` 属于系统元数据，不参与摘要，发布时应剔除。符号链接仍禁止，不得借元数据排除规则跳过真实代码审核。
- 供应连接创建时必须显式选择已启用且兼容的适配器。供应插件遵循公共 `app/shared/plugin/contract/ProviderAdapterInterface` SDK v1 与 `plugin.json`、`configuration.schema.json`；供应商字段、目录名称及关系校验放在插件中，核心服务和前端不得按供应商名称追加分支。已有连接不切换适配器，绑定封存插件版本与清单摘要，版本变化先重测。当前契约及能力边界见 `docs/development/provider-adapters.md`。
- 插件必须通过 Core 定义的 Contract、事件和 DTO 交互，不得直接修改核心领域对象、核心表结构或依赖内部实现类。
- 每个插件声明配置字段及所需能力，包内只保存 Schema，不保存客户密钥；插件设置、连接设置和产品绑定分开管理，多个连接配置隔离。宿主负责表单、白名单校验、敏感值加密、版本与测试状态，插件仅通过固定配置方法补充平台规则。
- 按类别提供必要接口与可选能力接口，宿主只调用已发布的固定方法和 DTO；不提供任意方法名执行、全局钩子或任意服务定位器。构造函数无外部副作用，不持有当前用户、请求或连接秘密；跨模块写入通过公开 Application 命令。原生 PHP 仍是受信代码，受限依赖注入及静态检查不构成恶意代码隔离。
- 短信和邮件的模板提交、审核查询为独立可选接口，由根目录入口实际实现情况识别，无需另增清单声明或空方法。受理不等于审核通过，申请引用与发送模板ID分开，超时保留unknown语义；调用方必须持久化申请、模板修订、原通道及配置修订，不能换默认账号查询或自动重发。见 [模板审核契约](../docs/plugins/message-template-review.md)。
- 通道插件采用最小接入形式，配置字段与固定发送方法由插件提供，宿主统一负责表单、加密、权限及发送记录。邮件插件的 `send(MailMessage, Configuration)` 直接实现 SMTP 或 HTTPS 发送；系统提供的 HTTP 快捷方法可直接使用，额外第三方客户端通过插件自己的 Composer 声明、锁定和构建。平台专有配置和协议实现留在插件内部。插件必须限制访问配置范围、设置超时并校验 TLS，不持有跨调用凭据。插件可按需使用本地 Composer SDK；使用供应宿主 HTTP 客户端时仍执行其连接和端点限制，不把 SDK 开放规则扩展为任意核心访问权限。
- 同系统多上游采购、成本计算、余额结算与链路防环属于核心上下游模块，不放入资源提供者插件；资源提供者负责外部平台执行，不决定本系统订单、账务及服务状态。
- 每个插件必须声明唯一 ID、版本、系统兼容范围、插件类型、权限、依赖、入口、迁移、静态资源及卸载数据策略。固定类别入口 `SmsAdapter.php/MailAdapter.php/ProviderAdapter.php` 等直接位于插件根目录，命名空间为 `plugins\<category>\<plugin_id>`；不创建或扫描 `api/` 入口目录。辅助代码按实际需要放入 `app/`，无需创建空层级。
- 插件安装包不得包含 `.env`、密钥、生产连接信息、日志、测试上传物、宿主依赖目录或前端源码依赖树；允许并要求交付插件自己的生产 `vendor/`，不得复制宿主 `vendor/`。
- 插件 Composer 依赖不设包名白名单，可按实际平台选择 SDK；依赖完整性、版本冲突、核心命名空间和安装脚本边界继续校验。系统提供公共 `HttpClient` 的 GET/POST/PUT/DELETE、POST 表单及通用请求，作为推荐快捷能力，不强制所有插件使用；供应插件调用宿主客户端时仍保持连接与清单端点限制。公开说明见 `docs/plugins/http-client.md`。
- 第三方插件自行引入的 SDK 声明在对应插件的 `composer.json`，提交 `composer.lock`；使用 `composer install --no-dev --no-scripts --no-plugins --prefer-dist --optimize-autoloader` 预构建。宿主校验锁定版本、包完整性及自动加载边界后加载本地依赖。禁止 Composer 安装扩展、插件根脚本、根自动启动文件和自定义 vendor 路径；依赖变更按审核升级及完整重启执行。同进程内同名 SDK 的不同版本拒绝混用，目录隔离不等于命名空间隔离。
- 官方插件的共用 SDK 可经项目明确决定后由宿主主 Composer 统一维护。本项目支付宝订单码支付和身份验证共用 `backend/composer.json` 中的 `alipaysdk/easysdk`，不在各自插件目录重复安装；第三方插件不得自行修改宿主 Composer。宿主锁文件与 SDK 一起交付，依赖变更需回归并完整重启。常驻进程中的支付宝配置必须每次创建独立 Kernel，禁止使用缓存首个商户配置的静态 Factory。
- 阿里云短信/邮件/OSS V2/验证码、腾讯云短信/邮件/人脸核身/COS/验证码与微信支付官方 SDK 放在各自插件目录的 Composer 中，随各自锁文件及生产 vendor 交付，不加入主 Composer。共享传递依赖必须锁定兼容版本，并通过宿主依赖加载器检查。七牛直接实现 REST 上传、管理及下载签名，不引入 SDK。通过官方模型、签名或支持注入的客户端接入宿主 HTTP，禁止反射调用 SDK 私有传输、修改 vendor、关闭 TLS 或隐式自动重试有副作用请求。每次显式传入连接配置，不缓存首个账号。
- 本地存储插件只能调用 `LocalObjectStoreInterface` 的逻辑分区和对象键；私有根目录由服务器 `config/storage.php` 设置，核心负责原子写入、软链接防护和 HMAC 下载。禁止给插件开放任意文件路径或让通道配置指定公开目录。
- 微信支付 JSON 通知保留原文及单值签名头，使用固定 JSON 能力接口核对信任锚、RSA、AES-GCM、商户、订单、金额和币种；核心在幂等入账事务提交后才能确认通知。平台错误响应未验签时不能解释为交易状态。
- 第三方登录由核心生成绑定服务端会话的 state，限时缓存并原子消费后才交换授权码。插件只返回经过平台验证的外部身份，禁止返回平台令牌或自行签发会员/管理员会话；按插件、应用、OpenID 唯一绑定，不按昵称匹配。详细边界见 `docs/plugins/cloud-channels.md`。
- 插件涉及前端时，客户服务器只安装预构建产物，不执行 `npm install` 或现场编译。
- 普通配置表单、附加字段和普通列表优先使用 Schema UI；云服务器等复杂产品的核心配置结构、组合校验、计价和生命周期必须由独立产品类型模块及专属页面承载，不得退化成万能 Schema 表单。扩展统一采用受信的预构建资源、公开 SDK 和受控 Slot/页面扩展点，不要求 iframe。运行时注册与加载另列建设计划，同域 JavaScript 属于受信代码，不构成安全隔离。
- 插件安装、升级和卸载由宿主生命周期服务执行，不运行包内任意 Shell、Composer 脚本或启动钩子；必要的自有数据迁移须审核并考虑幂等、事务或补偿、失败恢复、版本兼容和明确的数据保留策略。插件自有表与核心表分开，未决资金、任务及存量资源引用未收敛时禁止卸载。
- 随发行包交付的官方基础通道由固定清单的前向迁移首次登记，保留安装/启用审计；已有安装状态、版本和包摘要不得覆盖，不自动启用任意第三方包，不创建商户或账号配置。短信、邮件支持类别级主用配置，存储支持默认存储；支付、第三方登录、实名认证、人机验证由具体业务选择，不允许统一默认。规则统一放在 ChannelCategories，前后端同步约束，历史业务引用不因调整主用策略改变。
- 应用商店分发经过构建、校验和签名的不可变安装包，不直接分发工作区源码。

## 主题规范

- 主题目录使用 `themes/<theme_id>/`，至少包含主题清单、模板、静态资源和预览图。
- 主题 ID 和模板名称必须通过白名单解析，禁止将请求参数直接拼接为模板路径。
- 第三方主题不得包含可执行 PHP 文件；模板变量默认转义，未经净化的数据不得使用 raw 输出。
- 主题模板不放入 `public/`；只有需要公开访问的版本化静态资源才能发布到公开目录。
- 主题上传和安装必须校验文件类型、路径穿越、压缩炸弹、系统兼容和完整性。每个主题 ID 仅保留一条已安装记录，同 ID 上传作为更新，保留兼容配置并补充新增字段默认值；不兼容时拒绝更新，禁止静默删除原配置。版本号只作包资料，资源继续按内容摘要隔离，发布后再原子更新当前记录。

## 数据与安全

- 消息配置由 `message_configuration` 核心模块维护固定事件、受众、可用渠道及变量。后台仅提供 view/update 权限的配置接口，不开放自由新增类型、任意模板执行或公开发送代理。整条消息配置加密持久化并以修订号控制并发；Webhook/加签密钥统一归属 system_settings 的非公开加密配置，不允许逐消息保存；全局配置只返回秘密标志，消息详情只返回机器人配置状态。空输入保留，清除需明确字段名；全局修改使用 settings 权限与独立修订，审计仅保留设置分类或消息编码与修订。邮件/短信启用前重新校验已配置通道并绑定其修订；配置保存不得隐式发信、发送短信或请求机器人。场景配置底层支持多个客户/内部/机器人接收组，按需兼容旧受众 JSON；社区版简化配置界面不能删除已有精细策略或历史任务，列表提供各受众固定目录元数据，保存仍保留完整修订及权限校验；双受众修订同事务提交，新结构禁止旧写入口覆盖。事件发布按声明受众执行，重叠范围的同账号同渠道去重，组标识/名称随任务封存，不修改历史已读或发送标识。详细说明见 `docs/development/message-configuration.md`。

- 所有新建表和字段必须设置中文 `COMMENT`；修改字段时同步检查并保留或更新注释，包括关联表、自动生成的主键、安装/升级记录以及插件自有表。PHPDoc、模型字段说明不能代替数据库注释。
- 注释说明业务含义，不仅重复字段名。状态写明当前已定义的取值，金额写明整数最小货币单位（人民币为分），容量、带宽、频率和耗时写明单位；关联字段写明对象及 NULL/0 的语义，JSON、快照、密文、哈希与脱敏字段写明用途，不记录真实个人信息、密钥或凭证样例。
- Phinx 新表使用 `table(..., ['comment' => '中文表说明'])`，字段使用 `addColumn(..., ['comment' => '中文字段说明'])`；自动主键需显式补充注释。已有结构补注释必须新增前向迁移，不修改已执行迁移，不覆盖客户已有中文注释。`MODIFY COLUMN` 必须保留原类型、长度、默认值、空值、字符集和全部其他属性，不得为补注释改变业务数据或索引。
- 注释验收必须在独立 MySQL 测试库验证全新安装、已有数据升级、自定义前缀、失败重试和结构/数据不变，并查询 `information_schema` 检查中文注释覆盖；SQLite 不支持原生 `COMMENT`，不能替代此项验收。实施说明见 [数据库注释规范](../docs/development/database-schema-comments.md)。
- 金额统一使用整数最小货币单位存储和计算，不使用浮点数参与结算。
- 数据库迁移必须可审查；不可逆变更需提供备份、灰度、前向修复或回退说明。
- 核心数据表结构统一通过 `database/migrations/` 中的 Phinx 迁移维护；首次安装和后续升级必须执行同一套迁移，不得在安装器、控制器、应用服务或发布脚本中另写一套建表或改表 SQL。
- 已提交、发布或可能在任一环境执行过的迁移文件不得修改；修复必须新增前向迁移。迁移使用无前缀逻辑表名，由迁移配置统一应用 `DB_PREFIX`。
- 系统升级统一通过 `php webman system:migration-status` 检查并使用 `php webman system:migrate` 执行；生产及非交互执行前必须完成数据库备份，禁止把直接运行 `vendor/bin/phinx migrate` 作为产品升级入口。
- 数据库迁移遵循扩展、迁移、收缩的兼容策略；删除字段、变更大表索引、批量数据回填等高风险操作必须明确锁表、执行时间、中断恢复和前向修复方案。
- 日志不得记录密码、Authorization、Cookie、完整支付数据和未脱敏个人信息。
- 所有运营后台、会员和插件接口必须分别完成认证、权限及对象归属校验。
- 上传、插件包和主题包必须校验内容、扩展名、MIME、大小、存储路径与访问权限，不能仅信任客户端元数据。
- 调用上游供应商和支付、短信、实名等外部服务时，必须设置超时、重试边界、幂等键、审计日志和脱敏策略。

## 业务日志功能的 IP 与位置规范

- 本节约束后续开发的业务日志功能，包括管理员操作日志、会员登录记录、认证与安全事件、订单及支付退款审计、插件操作记录等需要持久化、查询或在后台展示的日志数据；不要求 PHP、Webman、Workerman、第三方依赖、运行时错误和普通调试日志统一记录 IP 位置。
- 业务日志的数据表、实体、DTO、接口契约和展示字段必须包含 `client_ip` 与 `client_ip_location`，并保存操作发生时的快照值；不得仅在展示时临时查询位置，也不得只把 IP 或位置拼接进不可检索的描述文本。
- 客户端 IP 必须由统一、可注入的客户端 IP 解析服务提供。只有请求确实来自配置中的受信任反向代理或 CDN 时，才允许采用其约定的转发 Header；不得在各业务模块直接调用 `$request->getRealIp()`，也不得无条件信任客户端可伪造的 `X-Forwarded-For`、`X-Real-IP` 等 Header。
- IP 位置统一使用 Composer 依赖 `zoujingli/ip2region` 3.x 解析。必须在 `app/shared/` 定义稳定的查询 Contract 或公共服务，并在 Infrastructure 中封装 `Ip2Region`；Controller、Application、Domain 及各业务模块不得直接调用 `ip2region()` 全局函数、直接实例化库类或自行解析返回字符串。
- `client_ip_location` 保存适合业务日志检索和展示的规范化位置文本。回环地址和私网地址分别记录为明确的“本机”或“内网”；IP 无效、数据库缺失或查询失败时记录为“未知”。位置解析失败不得阻断原业务操作或导致业务日志整体写入失败。
- 必须同时考虑 IPv4 与 IPv6。发行包若声明支持 IPv6 位置查询，必须包含并校验对应的 ip2region IPv6 数据库；未包含数据库时按统一降级值处理，不得在业务请求期间联网下载或更新位置数据库。
- 由用户操作派生且异步写入的业务日志，必须在消息元数据中显式传递操作发生时的 IP 和位置，不能在消费者执行时改记队列服务器地址；纯系统定时任务若需要生成业务审计记录，两个字段使用 `null` 并明确标记操作主体为系统。
- IP 和位置只用于业务审计、安全分析和故障定位，不得作为认证、授权或风控的唯一依据。新增相关日志功能时，至少测试直连请求、受信任代理、伪造转发 Header、IPv4、IPv6、私网、无效 IP、位置库异常和异步写入，并覆盖查询权限、数据保留和清理策略。

## 接口返回与异常处理规范

- 所有 `/api` 接口（包括 Controller、中间件、异常处理器和插件接口）统一使用 `app/shared/http/ApiResponse.php` 生成 JSON，禁止手写 `json_encode()`、直接调用 `json()`，也不得自定义另一套响应字段。
- 响应固定包含 `code`、`message`、`data`、`request_id` 四个字段；响应头必须同步返回 `X-Request-Id`。成功时 `code` 必须为 `0`；失败时 `code` 必须为稳定且非零的业务错误码，`data` 没有内容时为 `null`，不得省略固定字段。
- 成功响应示例：`{"code":0,"message":"ok","data":{},"request_id":"..."}`。失败响应示例：`{"code":42200,"message":"参数校验失败","data":{"errors":{"name":["名称不能为空"]}},"request_id":"..."}`。
- HTTP 状态码表达协议层结果，业务错误码表达可供程序判断的失败原因，二者不得混用。禁止“所有请求都返回 HTTP 200”；常用状态为 400 参数格式错误、401 未认证、403 无权限、404 资源不存在、409 状态冲突、422 业务或字段校验失败、423 资源锁定、429 请求过多、500 未预期异常、503 服务不可用。
- 通用错误码定义在 `app/shared/http/ApiErrorCode.php`，默认采用五位编码；具体业务域可以定义更细的稳定错误码，但发布后不得改变已有错误码的语义，也不得把数据库错误号、第三方原始错误码或异常行号直接作为接口错误码。
- 可预期且可安全展示的失败统一抛出 `app/exception/BusinessException.php` 或其语义明确的子类。Controller 不得为每个业务异常重复 `try/catch`，由 `app/exception/Handler.php` 统一转换响应。
- 字段校验错误放入 `data.errors`，键为稳定字段名，值为字符串数组；批量操作错误放入 `data.items` 并携带业务对象标识。不得只拼接一段无法被前端定位字段的文本。
- 基础设施层捕获 PDO、Redis、网络、支付或供应商 SDK 异常时，必须使用 `$previous` 保留异常链，再转换为本系统异常；不得把连接串、SQL、密钥、第三方响应原文或堆栈暴露给客户端。
- 未预期异常必须由全局异常处理器记录完整服务端日志，API 仅返回错误码 `50000` 和通用提示，生产或调试环境都不得在接口中返回堆栈、文件路径、SQL、配置或密钥。
- 业务异常属于预期分支，默认不写系统错误日志，避免污染告警；登录失败、越权、支付、退款等安全或资金事件必须另写脱敏的审计日志。禁止空 `catch`、吞掉异常或仅记录日志后继续返回成功。
- 日志必须携带同一请求的 `request_id`、HTTP 方法、路径和必要的脱敏业务标识；不得记录密码、令牌、Cookie、Authorization、完整身份证号、银行卡号或第三方密钥。不得将查询字符串整体写入异常日志。
- 外部服务错误必须在 Infrastructure 边界转换为本系统稳定错误码和用户可理解的信息；原始异常只留在服务端日志。重试耗尽、熔断、超时和幂等冲突要使用不同错误码，便于监控和前端处理。
- 新增或修改接口时，至少测试成功响应、业务异常、权限/状态异常和未预期异常，断言 JSON 固定字段、HTTP 状态码、业务错误码及 `X-Request-Id`；不得只断言提示文字。

## 后端验证

根据变更范围选择并执行：

```bash
composer validate --no-check-publish
find app config support -type f -name '*.php' -print0 | xargs -0 -n1 php -l
vendor/bin/phpunit
```

- 修改路由、中间件、进程、事件、队列或定时任务时，补充对应的集成验证，并关注多进程及常驻内存行为。
- 修改数据库、Redis、外部接口或插件生命周期时，验证失败路径、幂等性和恢复策略，不能只覆盖成功路径。
- 无法运行依赖真实服务的检查时，明确列出未验证项和所需环境，不得用 Mock 或静态检查代替生产集成结论。

- 会员注册支持手机号或邮箱加密码，两种方式与各自验证码要求由系统设置控制；`register_verification` 支持短信和邮件，`login_verification` 仍只允许短信渠道。目录、单条及批量配置保持一致；注册验证码由独立服务校验有效期、单次消费和频率限制，不经过普通通知队列或消息日志。新生成的对外会员 ID 使用九位固定随机数字，读取与登录兼容历史八位编号，列表按注册时间及内部主键稳定排序，业务外键仍使用内部主键。

- 云服务器预付费v2按schema_version分派，历史v1继续读取；付费周期及优惠按可用区独立校验、封存和计价，显式可用区规则缺失不能回退全局周期，旧发布快照按原规则兼容；发布时封存线路网络、周期规则和供应参数映射。实时库存通过ComputeInventoryRepositoryInterface独立处理，固定锁顺序库存池→预占；正式占用未经供应释放确认不能恢复。社区模式明确拒绝按量、流量及密钥登录。后台购买订单已接入余额付款与逐实例库存占用；会员自助购买及供应履约尚未接入，实施边界见docs/development/order-management.md与docs/development/cloud-server-prepaid.md。

- 官网公共配置与系统、主题分别维护：平台品牌和备案在系统设置，公司资料在官网基础设置，导航与页面SEO分别维护；首页副标题与逐页SEO由页面SEO管理，不提供全站默认SEO配置；主题只保存展示配置。模板通过 `site.company` 读取公开公司资料。基础和导航按独立权限、字段白名单及共享 revision 保存，不能跨分区覆盖。

- 会员主题仅支持console/pc（必备）与console/mobile（可选），不接受responsive新包。移动端开关由统一绑定维护，只有实际会员主题包含有效mobile入口才能开启；关闭时所有设备及显式偏好均使用PC。旧目录仅在历史迁移重放与快照转换时使用冻结契约。

## 授权码激活与官网更新

- 当前官网接入采用授权码激活和安装签名，不采用配对码、官网账号确认或Access/Refresh Token。授权码只在激活请求发送，不进入加密状态、日志或浏览器存储；本机权限和同源写入保护继续执行。
- 许可证与发行公钥分别预置，原始UTF8载荷验签后再判断安装/连接/修订及期限；新版未知kid不能由下载接口自动信任。
- 续费保留原安装和授权码，按官网已付事实同步证书；历史更新按首次发布时间核对更新期，不把合法到期的购买版本改成community。
- 系统任务登记真实发行/包和固定目标，执行时重新取得同一目标清单，按实际安装及重启核实后回报；回报失败只重试报告，不重做安装。保留.env、私有身份及客户插件，迁移后失败不盲目旧代码回滚数据库。
