# 云产品平台架构与开发方案

## 1. 文档状态

本文定义皓量云擎云业务运营系统云产品平台的目标架构、模块边界、公共契约、交易流程和分阶段交付要求。

文中的能力按以下状态理解：

- **当前实现**：后台权限、登录与操作日志、系统设置、在线安装和数据库升级等基础能力已经存在；订单只读查询和财务记录只读查询、资金表结构及部分内部余额记账能力已经落地，参见 [财务管理实施状态](../development/finance-foundation.md)。
- **确定设计**：独立产品类型域、公共交易、可靠履约、插件、主题和上下游协议按本文建设。
- **后续扩展**：物理服务器、域名、SSL 证书、用量后付费、授信、账期和进程级插件隔离，在云服务器闭环稳定后增加。

当前代码中出现的产品、订单、上游、退款等菜单或权限名称不代表相应业务已经实现。具体供应商版本、接口范围及真实联调结论记录在对应适配器文档中，不在本文中预先宣称。

## 2. 架构结论

平台采用 **Webman 模块化单体 + 独立产品类型域 + 公共交易能力 + 外部服务插件**。

- 每个客户独立部署，使用自己的数据库、域名、支付账户和外部服务凭证。
- 首个完整产品类型为云服务器，首个生产适配器为魔方云。
- 首期支持小时、天、月、年预付费、一次性费用和试用。
- 上下游采用逐级采购、独立销售、独立定价和预存余额结算。
- 每个产品类型拥有自己的配置模型、管理页面、购买页面和生命周期。
- 第三方插件首期采用审核后本地安装的原生 PHP 插件；原生插件属于受信代码，不把开发规范描述为安全沙箱。
- 当前保持单体部署和单一安装包。只有形成明确的独立扩缩容或安全隔离需求后，才拆分服务或增加独立插件进程。

MySQL 是订单、资金、服务、履约任务和事件投递状态的事实来源。Redis 用于缓存、限流和任务通知，不能作为关键业务结果的唯一存储。

现有模型、付款事务及服务首次来源整改见 [现有系统与 ORM 重构实施说明](current-system-refactor.md)。该整改不代表真实支付或云产品履约已经完成。

## 3. 业务模块边界

### 3.1 核心模块

| 模块 | 职责 |
| --- | --- |
| 产品注册与展示 | 注册产品类型，维护产品名称、分类、购买入口、发布版本和展示状态 |
| 云服务器 | 管理地域、规格、镜像、存储、网络、防护、组合约束和配置计价 |
| 物理服务器 | 管理设备库存、机房、硬件配置、独占预留、装机和回收 |
| 域名 | 管理后缀、可注册查询、联系人、注册、转入、续费和赎回 |
| SSL 证书 | 管理证书类型、域名数量、申请资料、验证、签发、重签和吊销 |
| 客户 | 管理会员身份、联系方式、客户分组、实名状态和资源归属 |
| 报价与订单 | 生成报价，处理新购、续费、变更、取消和订单明细 |
| 支付与账务 | 管理支付、退款、余额、冻结、采购成本和不可变业务台账 |
| 服务 | 管理已交付实例、订阅期限、试用状态和服务可执行操作 |
| 履约 | 管理开通、续费、重装、调整、暂停、释放及失败恢复 |
| 供应 | 管理外部连接、供应目录、供应绑定、成本报价和采购单 |
| 同系统对接 | 管理合作方、上下游协议、商品导入、采购关联、通知和对账 |
| 扩展与门户 | 管理插件、官网主题，以及文件、通知、支付、实名等能力的调用编排 |

产品、报价、订单、账务、履约和上下游同步具有复杂状态和业务不变量，使用领域模型保护规则。普通配置和查询保持精简，不机械创建空领域层。

跨模块业务写入与协作使用公开 Application 门面或 Contract，不访问对方 Model 或仓储实现。后台复杂联表展示查询允许在 Infrastructure 专用只读实现中访问相关表，显式选择安全字段。可靠异步协作使用持久化任务、Outbox 和幂等消费者。

### 3.2 四个独立概念

| 概念 | 含义 |
| --- | --- |
| 产品类型 | 定义某类产品的配置语义、校验规则、计价扩展和生命周期，例如云服务器 |
| 销售产品 | 商户发布的具体销售方案，例如“香港通用型云服务器” |
| 供应绑定 | 指定使用哪个连接、资源池和参数映射交付某个销售版本 |
| 服务实例 | 客户已经购买并交付的实际资源，保存独立资源标识和服务状态 |

同一销售产品可以配置多条供应线路，但每份有效报价只能选择一条能够完整交付当前配置的供应绑定。外部结果未知时，不能自动切换线路再次创建资源。

## 4. 云服务器产品类型

### 4.1 结构化配置模型

云服务器的关键配置使用专属领域模型，不能用一张通用属性表或任意键值 JSON 代替。

| 配置领域 | 主要内容 |
| --- | --- |
| 部署位置 | 地域、可用区、网络线路及其可售关联 |
| 计算规格 | 规格组、规格、CPU、内存和架构 |
| 镜像 | 镜像类型、系统版本、架构、登录要求和兼容条件 |
| 存储 | 系统盘、数据盘列表、磁盘类型、容量、数量和步长限制 |
| 网络 | 带宽计费方式、带宽范围、IP 类型、数量和网络配置 |
| 防护 | 防护方案、档位和适用线路 |
| 初始化 | 主机名、登录方式、账号和凭证引用 |
| 购买条件 | 周期、数量和试用申请 |

供应商不支持用户选择的参数时，销售配置可以使用经过校验的固定值，购买页面不展示无意义的选项。

数据盘使用结构化列表，支持增加和删除多块磁盘。密码、私钥等敏感信息写入独立凭证存储，订单和生产请求只保存短期凭证引用；日志、产品版本和公开报价中不得出现明文。

地域、可用区、线路、规格和镜像使用系统内部稳定标识。供应商专有标识保存在供应映射中，不能进入核心产品模型。

### 4.2 四类数据分别管理

#### 配置资源

地域、可用区、线路、规格、镜像和磁盘类型等基础资源。支持手工维护和供应商同步，记录来源连接、外部标识、同步时间及可用状态。

#### 销售配置

商户选择可销售的资源，配置默认值、组合限制、价格、购买资格、试用和退款政策。销售配置通过完整性检查后发布为不可变版本。

#### 购买配置

客户在一次购买中形成的具体选择。系统对其标准化、校验和计价，并写入报价快照。

#### 服务实例

已经交付的资源。保存实际供应连接、外部资源标识、交付配置、服务期限和支持的生命周期操作。

编辑销售配置不能改变既有报价、订单和服务。供应商目录同步也不能直接覆盖商户已经发布的销售版本。

### 4.3 专属管理页和购买配置器

云服务器后台配置页面按以下业务区域组织：

- 基本信息和销售状态。
- 地域、可用区和线路。
- 规格组和规格。
- 镜像类型和镜像。
- 系统盘、数据盘、带宽、IP 和防护。
- 周期价格、配置加价、试用和退款规则。
- 供应连接、资源池和字段映射。
- 购买预览、报价预览和发布检查。

官网云服务器购买页面使用专属配置器，依次处理地域、可用区、线路、规格、镜像、系统盘、数据盘、带宽、IP、防护、初始化信息、周期和数量。

复杂产品的关键结构和交互使用专属组件。Schema UI 仅用于普通配置表单、附加字段和适合通用渲染的插件界面，不能承担云服务器的核心联动、磁盘列表或价格计算。

### 4.4 联动、校验和计价

云服务器类型提供三项稳定能力：

| 能力 | 输入 | 输出 |
| --- | --- | --- |
| 可选项解析 | 销售版本、客户上下文和当前选择 | 可选值、限制、不可选原因和失效选择 |
| 完整配置校验 | 完整购买配置 | 标准化配置、字段错误和组合错误 |
| 配置计价 | 已校验配置、周期和数量 | 分项费用、计价依据和供应绑定 |

典型规则包括：

- 地域约束可用区和线路。
- 可用区及线路约束可售规格和网络能力。
- 规格约束镜像架构、磁盘类型和数据盘数量。
- 镜像约束登录方式和系统盘最低容量。
- 线路约束带宽范围、计费方式、IP 和防护方案。

前端选择变化后请求可选项解析，并清理已经失效的选择。报价和下单分别执行服务端完整校验。系统按需解析组合，不为所有可能组合预先创建商品。

## 5. 公共契约

### 5.1 产品与履约契约

| 契约 | 责任 |
| --- | --- |
| `ProductTypeDefinition` | 声明类型标识、契约版本、配置结构、必需能力和页面入口 |
| `ProductTypeHandlerInterface` | 解析选项、校验配置、计算类型价格并构建生产请求 |
| `Quote` | 封存金额、费用明细、有效期、配置、销售版本和政策快照 |
| `ProvisioningRequest` | 传递标准生产参数、供应绑定、操作编号、幂等键和期限 |
| `OperationResult` | 表示成功、已受理、明确失败或结果未知 |
| `CapabilityManifest` | 声明插件和具体连接支持的类型、动作、限制和契约版本 |

类型模块负责理解规格、镜像、磁盘和网络等业务语义；公共报价模块负责金额规则、报价有效期和快照封存；供应插件负责把标准请求转换为外部系统参数。

公共契约使用版本化 DTO 和 Schema 发布。兼容性变更增加可选字段；破坏性变更发布新主版本。运行中的订单和服务固定引用创建时的契约与供应映射版本。

### 5.2 API 入口

| 入口 | 用途 |
| --- | --- |
| `/api/admin/v1` | 运营后台管理 |
| `/api/console/v1` | 会员购买与服务管理 |
| `/api/public/v1` | 官网公开产品、公开配置和受限回调 |
| `/api/partner/v1` | 独立实例之间的上下游机器调用 |

插件 API 继续使用 `/api/<入口>/v1/plugins/<plugin_id>` 前缀。所有接口分别完成身份认证、细粒度权限、对象归属和业务授权，不能用菜单隐藏替代服务端校验。

## 6. 报价、订单、支付和账务

### 6.1 交易闭环

标准新购流程：

```text
配置选择
  -> 类型校验
  -> 生成报价
  -> 创建订单
  -> 支付确认
  -> 写入履约任务
  -> 外部生产
  -> 交付确认
  -> 服务生效
```

- 报价保存类型版本、销售版本、标准化配置、供应绑定、价格、试用及退款政策快照。
- 订单只接受当前有效且归属正确的报价，由服务端确定应付金额。
- 支付状态、订单状态、服务有效状态和资源运行状态分别建模。
- 服务确认交付后开始账期；外部平台有明确计费起点时，同时记录该时间用于成本核对。
- 续费生成新的报价和订单，上游确认续期后才更新服务有效期。
- 已付款订单的金额不随商品调价变化，调价通过新销售版本生效。

### 6.2 计费

首期支持：

- 小时、天、月、年预付费。
- 一次性初始化费用。
- 规格、磁盘、带宽、IP 和防护等配置加价。
- 试用订单及试用生产成本记录。

用量后付费在后续通过独立计量、定价、账单和更正模型扩展，不能把用量记录塞入预付费订单。

金额使用最小货币单位和确定的舍入规则，不使用浮点数参与结算。默认币种为人民币，同时保留币种字段；系统不隐式执行汇率换算。

### 6.3 账务

账务采用可对账的不可变业务台账：

- 区分余额、冻结、收款、退款、采购和人工调整。
- 已入账记录不直接修改，通过冲正和调整分录纠错。
- 支付、退款和上下游交易使用唯一外部交易标识去重。
- 余额冻结、释放和扣减在数据库事务内完成，并使用行锁或等效并发约束。
- 退款申请先冻结可退余额，累计成功退款与处理中退款不能超过可退金额。

支付插件只负责渠道下单、查询、关闭、退款和验签。核心系统验证商户、订单、币种、金额和重复回调，并决定订单及账务状态。

## 7. 可靠异步履约

支付确认后的订单变更、账务记录和 Outbox 记录在同一数据库事务中提交。投递进程将持久化事件发送到 Redis 队列，消费者根据业务标识重新读取数据库状态。

Webman `event` 用于进程内、短小且允许同步完成的解耦逻辑。开通、退款、通知和上下游同步使用持久化任务，不能把同步事件当作可靠消息队列。参考 [Webman Event 文档](https://www.workerman.net/doc/webman/components/event.html)。

履约任务至少保存：

- 操作编号、服务标识、操作类型和幂等键。
- 标准请求快照、供应连接和契约版本。
- 当前状态、状态版本、执行租约、尝试次数和下次执行时间。
- 外部任务编号、外部资源标识和最后查询结果。
- 错误分类、脱敏摘要和人工处理状态。

执行结果统一为：

- `succeeded`：已经确认成功。
- `accepted`：外部系统已经受理，后续继续查询。
- `failed`：已经确认失败，可以按规则补偿。
- `unknown`：请求是否产生副作用未知，必须先核查。

必须处理消息重复、消息丢失、Worker 崩溃、回调重复、回调乱序、外部超时和状态查询失败。Redis 消息丢失后，由数据库任务恢复投递。同一服务上的重装、续费、释放等冲突操作必须串行化。

外部写操作超时后，禁止立即重发或改用另一供应商。优先通过外部幂等键、业务标签、外部任务编号或资源查询确认真实结果；无法自动确认时进入人工处理队列。

## 8. 试用、续费和退款

### 8.1 试用

- 按销售版本设置开关、期限、允许配置、客户资格、限额和到期策略。
- 试用同样创建订单、履约任务和服务记录，生产成本正常记账。
- 转正式时，供应能力允许的产品沿用现有资源，避免重复创建。
- 到期按版本中确定的通知、暂停、保留和释放策略执行。
- 默认由用户主动购买转正式，不执行未明确授权的自动扣费。

### 8.2 续费

- 为当前服务生成新的续费报价并校验服务状态。
- 需要上游续期时，等待上游确认后再更新本地有效期。
- 上游结果未知时保留处理中状态并进入对账，不能提前宣告成功。
- 已收款但明确无法续费时，进入退款或人工处理流程。

### 8.3 退款

退款政策随销售版本发布，明确可退项目、期限、计算方法及不可退费用。

终止型退款必须核实资源释放结果，避免退款后继续产生供应成本。“退给客户”和“向上游追回采购款”是两笔独立业务；上游拒绝退款时，由当前商户根据自己的销售承诺处理客户退款并记录损失。

## 9. 插件体系

### 9.1 插件类型

| 插件类型 | 插件职责 | 核心职责 |
| --- | --- | --- |
| 产品类型扩展 | 提供类型定义、专属校验、生命周期扩展和专属页面 | 注册类型，提供交易、账务和履约公共能力 |
| 资源生产与供应 | 查询供应目录，创建、查询、控制、续费和释放资源 | 调度任务，维护服务归属、幂等和业务状态 |
| 文件存储 | 读写、删除、临时访问地址 | 上传授权、文件元数据和访问控制 |
| 邮件、短信 | 调用渠道发送并查询状态 | 模板、收件人、通知策略和发送记录 |
| 支付 | 渠道下单、查询、关闭、退款和回调验签 | 应付金额、订单状态、退款资格和账务 |
| 实名认证 | 发起认证、查询并转换渠道结果 | 业务准入、实名状态和最小化信息保存 |

一个插件可以提供多个能力，一个插件也可以创建多个连接实例。插件版本、连接配置和产品供应绑定必须分开管理。

### 9.2 插件清单和生命周期

每个插件包声明：

- 唯一 ID、版本、许可证和来源。
- 兼容的 Core、PHP 和 SDK 版本。
- 能力、路由、权限、任务和配置 Schema。
- 数据库迁移、依赖、静态资源和卸载数据策略。
- 示例配置、开发文档、契约测试和升级说明。
- 安装包完整性和签名信息。

生命周期为：

```text
校验 -> 安装 -> 配置 -> 连通性及能力测试 -> 启用
     -> 停止接单 -> 排空任务 -> 升级或卸载
```

仍有运行服务、处理中资金任务或未完成履约任务时，禁止直接卸载。插件数据默认保留。客户服务器只加载预构建资源，不在运行时执行前端依赖安装和编译。

Webman 应用插件提供代码、配置和生命周期的组织基础，但插件路由仍进入全局路由表，原生 PHP 代码也具有宿主进程权限。首期只允许审核后的受信插件；不把命名空间、配置前缀或 iframe 描述为服务端安全隔离。参考 [Webman 应用插件文档](https://www.workerman.net/doc/webman/plugin/app.html)。

## 10. 官网主题和前端扩展

官网采用 Webman 服务端渲染、Twig 主题和预编译交互组件。

- 主题控制首页、导航、页脚、产品介绍、购买页面外观和品牌配置。
- 产品类型控制配置器的业务结构、联动、校验和报价行为。
- 每个产品类型提供默认购买页面；主题缺少专属模板时回退默认模板。
- 服务端始终重新校验配置、价格、权限和购买资格。
- 主题只接收整理后的数组和标量，不接收数据库连接、容器或领域实体。
- 模板变量默认转义，主题 ID、模板名和静态资源路径使用白名单解析。

后台、会员控制台和官网可以共享版本化 TypeScript DTO、Schema 及纯规则工具，但不能跨应用直接引用页面源码或 React Context。运营后台使用 Arco Design，会员控制台使用 Ant Design；各自实现与设计系统匹配的专属配置器。

普通插件表单和附加字段使用主应用控制的 Schema UI。专属页面和小型扩展均采用受信预构建资源，通过公开 SDK 与受控扩展点接入。SDK 明确数据、路由、权限、动作与主题能力，不依赖主应用私有 Context 或内部 API。同域 JavaScript 属于受信代码；运行时注册、加载、升级兼容和失败回退留在插件阶段实现。

## 11. 多级上下游协议

每一级独立维护自己的销售订单、采购单、服务映射、余额和资金流水。

```text
终端客户 -> A 商户 -> B 上游 -> C 上游 -> 实际资源平台
```

业务层不固定代理级数。每一跳持久化本地交易后异步请求直接上游，结果通过通知和主动查询逐级传播，不能用一条同步 HTTP 请求贯穿所有层级。

协议覆盖：

- 产品类型及连接能力发现。
- 可售配置和版本导出、导入。
- 报价、采购、续费、服务操作和退款。
- 余额查询、冻结、扣款、释放和流水查询。
- 状态通知、操作查询和周期对账。

每个安装实例具有稳定实例标识。请求携带已经经过的实例链路，用于检测循环供应关系；同时设置可配置的技术跳数上限，避免异常请求无限传播。

上游商品导入后形成当地商户自己的销售配置，不直接覆盖已发布版本。各级只向直接合作方暴露已授权的数据，不传播供应凭证、原始供应链或未经授权的成本。

上游余额以其账本为准：受理采购时冻结，成功后扣款，明确失败后释放，结果未知时保持冻结并进入对账。多级系统之间不建立分布式数据库事务。

`/api/partner/v1` 使用 TLS、合作方身份、请求签名、时间戳、随机数和业务幂等键，并支持密钥轮换。重复幂等键与相同请求返回原结果；相同幂等键对应不同请求时返回冲突。

## 12. 权限和审计

核心权限与已校验插件声明共同组成可授权权限目录。每个新页面同时提供页面访问权限和实际操作权限。

产品类型至少定义：

- 查看和配置权限。
- 发布和调价权限。
- 供应映射和连接使用权限。
- 开通、重装、暂停、续费和释放权限。
- 试用审批和退款权限。

会员接口检查资源归属；合作方接口检查合作账户、商品授权和操作范围。前端菜单和按钮只用于交互提示，不能代替服务端授权。

支付、退款、余额调整、供应映射变更、插件生命周期和人工处理必须写独立业务审计。审计保存必要的业务标识和脱敏摘要，不记录密码、密钥、Cookie、Authorization 或第三方完整原始报文。

## 13. 实施路线

| 阶段 | 交付目标 | 完成条件 |
| --- | --- | --- |
| A：产品契约 | 云服务器结构、联动、销售版本、报价和供应绑定模型 | 关键类型契约及失败路径评审通过 |
| B：执行基础 | 队列配置、持久化任务、Outbox、凭证管理、插件注册和权限 | 任务可从崩溃、重复和投递丢失中恢复 |
| C：交易闭环 | 专属配置页、购买配置器、客户、订单、支付、账务和服务管理 | 模拟供应商完成新购、续费、试用和退款 |
| D：真实生产 | 对接确认版本的魔方云并完成能力清单 | 真实测试环境完成资源创建、查询、管理和释放 |
| E：上下游 | 商品导入、采购、余额和服务状态传播 | 三套独立实例完成交易及故障恢复 |
| F：生态扩展 | 发布 SDK、主题样例，增加其他类型和供应商 | 外部开发者能按公开规范完成独立扩展 |

首个可售版本以 A 至 E 完成为目标。公共 SDK 先通过云服务器真实闭环验证，再作为稳定接口对外发布。

## 14. 验收门槛

### 产品与报价

- 更换地域、可用区、线路、规格或镜像后，失效选择能够清理并说明原因。
- 数据盘、带宽、IP、防护和初始化参数能正确校验和计价。
- 不可交付的组合不能生成有效报价。
- 修改销售版本不影响既有报价、订单和服务。
- 报价过期、归属错误、供应能力变化均得到明确处理。

### 支付、账务和退款

- 重复或伪造支付回调不会重复入账或改变错误订单。
- 并发余额扣减、冻结、释放和退款不会产生负余额或超退。
- 退款渠道结果未知时可以查询、恢复或转人工处理。
- 向客户退款与向上游追回采购款能够独立追踪和对账。

### 履约与恢复

- Worker 在外部成功后、写回数据库前崩溃，不会重复创建资源。
- Redis 消息丢失后能够从数据库任务恢复。
- 重复任务、回调乱序、外部超时和状态查询失败能够安全收敛。
- 冲突的服务操作不能并发破坏资源状态。

### 试用和上下游

- 重复试用、配额并发、到期任务重跑和转正式得到正确处理。
- A、B、C 三套独立实例在任一级断线、余额不足和通知乱序时可以恢复。
- 循环供应关系被拒绝，供应凭证和未授权成本不会向下游泄露。

### 插件、主题和权限

- 插件兼容性、能力缺失、安装失败、任务排空、升级和卸载保护得到验证。
- 主题模板回退、默认转义、路径限制和窄屏购买流程得到验证。
- 无页面权限、无操作权限、会员越权和合作方越权均由服务端拒绝。

真实供应商、支付、短信和实名认证的生产验收必须使用授权测试环境。Mock、静态检查、构建成功或 HTTP 200 不能代替外部资源和资金结果验证。

## 15. 运行与发布要求

- 核心和插件数据库结构通过受控迁移维护；生产升级前备份并检查兼容性。
- 客户发行包包含 Composer 生产依赖和预构建前端资源，服务器不依赖 Node.js。
- 修改插件代码、路由、进程和启动配置后执行 Webman restart，并在真实进程环境验证。
- 升级前停止领取新的履约任务，排空或安全转移在途任务，再替换代码和重启。
- 监控任务积压时间、结果未知数量、资源开通失败率、退款积压和对账差异。
- 同一安装实例扩展为多节点前，将本地文件迁移锁升级为跨节点共享锁或外部部署锁。

本文描述的是目标架构和开发门槛。只有相关迁移、接口、页面、测试和真实环境验收完成后，才能将对应能力标记为当前实现。
