# 系统缺陷与优化建议

基准日期：2026-10-10。适用范围：当前 `howstack-bos` 工作区。配套图册：[整个系统的架构](system-architecture.md)。

总体判断：模块化单体、产品类型契约、实例金额单元、资金来源追踪和消息数据库任务的方向合理。主要问题是 **交易闭环尚未完成、部分前后端能力不同步，以及发布环境和验收门禁不完整**。建议先完成一个可恢复的社区版云服务器购买闭环，再扩展产品和商业功能。

本报告区分三种结论：**确认缺陷**有明确代码冲突；**未完成能力**说明当前不能提供的业务；**条件风险**仅在特定规模或部署方式下成立。没有把推测写成已发生故障。此处是架构与落地评估，不是完整安全审计或生产性能报告。

## 1. 优先级清单

## 2. 发布环境不一致

### A01 容器与项目 PHP 要求冲突

**依据**：[Dockerfile](../../backend/Dockerfile) 使用 `php:8.3.22-cli-alpine`；[composer.json](../../backend/composer.json) 要求 `php >= 8.4`。现有 Docker Compose 是源码目录挂载和单 Webman 服务，`deploy/` 为空。

**影响**：按现有容器方案无法满足 Composer 平台要求；不能把本机 PHP 8.4 测试通过当作容器交付成功。

**建议**：

1. 统一 PHP 8.4 运行基线，按宿主和已交付插件核对扩展，而不是只满足某个 SDK。
2. 分开开发与生产部署；生产使用完整发行包或不可变镜像，提供 MySQL/Redis 配置与持久化要求。
3. 构建核心生产依赖、全部插件生产依赖、后台/控制台/安装器与 API 文档。发行构建不依赖客户服务器临时安装 npm 或 Composer 包。
4. 配置同源 HTTPS、公开目录、私有备份、进程管理和健康检查。

**验收**：干净环境构建；`composer check-platform-reqs` 核对宿主及插件；从空库安装；重启后登录、数据库读写、队列消费和私有文件保护通过。单纯镜像构建成功不足以完成验收。

## 3. 交易与交付闭环

### A02 缺少单实例履约

**依据**：[余额付款用例](../../backend/app/modules/order/application/PayOrderByWalletService.php) 提交付款、库存和事件；[实例单元模型](../../backend/app/modules/order/infrastructure/model/OrderItemUnitModel.php) 只包含金额与服务关联；[供应 SDK](../../backend/app/shared/plugin/contract/ProviderAdapterInterface.php) 只有认证、目录和绑定校验。

**影响**：客户付款后无法自动开通；不能记录三台中两台成功、一台失败的生产过程。付款已成功不等于订单已交付。

**建议**：按订单实例单元创建独立履约任务，持久化业务操作、供应连接/版本、幂等标识、外部任务/资源标识、状态、租约与尝试。数据库提交后才访问供应商，成功后在事务中关联服务并更新聚合进度。结果未知先查单或对账，不直接再开一台。

订单支付、履约进度、服务有效期和资源运行状态分开。部分失败可以在政策允许时退款对应单元；释放库存必须与未生产或已确认资源释放的事实匹配，不能靠手工改服务状态替代供应释放确认。

**验收**：三台独立成功/失败；重复消费不重复开通；开通成功但本机断电后可查询恢复；关停/退款竞争不超退或重复释放；旧 Worker 不能覆盖新租约；每台都有可审计过程。

### A03 交易 Outbox 缺少投递和消费

**依据**：[DatabaseOutboxWriter](../../backend/app/modules/finance/infrastructure/DatabaseOutboxWriter.php) 明确只写 `finance_outbox`；已有 [MessageDeliveryWorker](../../backend/app/process/MessageDeliveryWorker.php) 维护的是消息任务。两者语义不同。

**影响**：`order.paid`、`refund.completed` 入库后没有可靠的交易后续执行。消息通知已投递也不能证明生产或上游退款已执行。

**建议**：补充交易事件发布器、消费去重和消费状态。事件唯一键保证事件唯一；消费者独立去重保证各下游只执行一次业务效果。可以复用租约、退避和安全错误编码的设计，保留不同任务状态和业务规则。初期使用现有 Redis 队列，不必引入新的消息中间件。

**验收**：提交后、入队前中断可补投；队列丢失可恢复；同事件重复到达无重复业务效果；消费失败可解释和恢复；未知外部结果不能被队列自动重投放大。

### A04 在线支付和原渠道退款未接入

**依据**：[PaymentChannelService](../../backend/app/modules/channel/application/payment/PaymentChannelService.php) 提供创建、查单、关闭和通知验签；当前通道控制器没有交易支付回调入口；[订单说明](../development/order-management.md) 明确当前开放余额付款。

**影响**：已经有支付宝/微信插件，但没有完整商户交易创建、回调入账、主动查单、关闭竞争、退款和对账链路。不能根据前端“支付成功”就更新订单。

**建议**：

- 锁定商户、通道修订、订单/充值业务、币种、金额与交易号。
- 验证原始通知、交易对象和付款事实；幂等提交后再确认回调，禁止重复充值和重复扣减。
- 外部超时进入未知状态，由查单恢复；付款与取消、关闭并发有明确处理规则。
- 原渠道退款保存独立尝试及退款幂等号，不把钱包退款假装为原渠道退款。
- 支付记录、资金流水、订单/充值事实可以进行核对，并保留差异处理记录。

**验收**：重复、伪造、金额不符、乱序回调；付款/关闭竞争；网络未知后的查单；重复退款；提交成功但回调响应丢失。外部沙箱和真实小额链路分别验收。

## 4. 账号和接口契约

### A05 前端登录能力超前于后端

**依据**：[控制台登录约定](../../frontend/console/login-integration.md)、[loginApi.ts](../../frontend/console/src/api/loginApi.ts) 和 [MemberAuthController](../../backend/app/modules/member/controller/MemberAuthController.php)。短信登录、微信/QQ 登录、找回密码是前端约定；`remember_me` 也尚未改变后端会话期限。

**影响**：用户看到入口后才得到“暂未接入”，也可能以为记住登录已经生效。OAuth 插件有 state 和身份交换能力，并不自动生成会员会话。

**建议**：后端提供明确的认证能力响应，前端按能力展示；随后按优先级完成独立登录挑战、重置挑战和第三方身份关联。第三方账号记录提供者、稳定外部身份和会员关系，建立唯一约束；不能仅按昵称或未验证邮箱自动合并会员。登录/注册/找回挑战分别绑定场景、账号和浏览器，并使用同一安全基础设施。

**验收**：公开能力与真实路由一致；验证码串场景失败；绑定冲突拒绝；账号禁用不可登录；重置成功旧密码会话失效；记住登录按服务端政策执行。

### A06 响应 Schema 不完整

**依据**：[响应缺口基线](../../tools/api-docs/response-gaps.v1.json) 当前列出 39 项；[文档流程](../development/api-documentation.md) 明确路由覆盖不等于字段覆盖。

**建议**：先补订单报价、财务动态资源、云配置和供应映射。动态资源使用明确的分类型 Schema 或 `oneOf`，写清整数分、ID 类型、状态、可空值和快照结构，避免万能对象。实现与消费者同步更新当前 `/v1`，未上线内部接口不新增无必要的旧别名。

**验收**：基线逐项减少；新增接口无豁免；真实响应通过 Schema 校验；关键错误也有明确结构；路由、权限、请求、响应和当前消费者保持一致。

### A07 文档状态漂移

**依据**：README 财务部分仍以记录查询和未开放办理描述，而 [财务办理说明](../development/finance-foundation.md) 已记录办理；[会员注册说明](../development/member-registration.md) 仍描述旧 `mobile` 登录参数，而当前控制器只收 `account`。

**建议**：修订被证实过期的能力说明；把“当前实现”“未来规划”“外部验收”分别列明。每次交付同步维护一份模块能力清单，并用路由和 Schema 检查约束接口事实。迁移、业务历史快照和第三方协议仍必须保留正确语义，不能作为过期文档一起删除。

**验收**：README、开发说明、OpenAPI 和真实接口不矛盾；新开发者能识别购买、付款、通知、开通分别完成到哪一步。

## 5. 产品规则和金额归属

### A08 新云计价耦合旧配置转换

**依据**：[PrepaidComputeTypeHandler](../../backend/app/modules/compute/domain/PrepaidComputeTypeHandler.php) 通过 `legacySnapshot/legacyNetwork` 等转换复用 [ComputeTypeHandler](../../backend/app/modules/compute/domain/ComputeTypeHandler.php)，新旧结构互相调用。

**性质**：维护风险，不据此认定现有计价错误。现有版本回放也有保留交易快照语义的必要。

**建议**：抽取无版本依赖的组合校验、磁盘约束和金额计算；当前新配置写入只采用最新结构。历史快照解读使用明确版本处理器或受控迁移工具，与当前输入解析分开。不要为减少代码直接改写已经产生的报价和订单快照。

**验收**：旧交易金额不变；新购买不经过多轮旧结构转换；不同可用区周期、双向带宽阶梯、赠送量、默认系统盘和镜像限制有覆盖；开放按量前能清晰隔离计费规则。

### A09 营销优惠缺少配置级归属

**依据**：[OrderUnitAllocator](../../backend/app/modules/order/domain/OrderUnitAllocator.php) 已按原价比例分摊整单应付，当前订单没有完整活动/优惠券办理。

**影响**：以后某优惠只适用于带宽、某规格或指定实例时，仅整单比例分摊不足以解释优惠作用对象；会影响退款和经营归因。

**建议**：先计算符合条件的费用分项优惠，再分摊订单级共同优惠。封存原价、活动、优惠券、折扣依据、费用分项、实付归属、优惠承担方与退款政策。报价、订单、退款和开票复用同一金额归属，不在退款时读取当前活动重新计算。

**验收**：特定配置优惠不扩散到无关配置；尾差稳定；多台部分退款、组合优惠、开票额度与整单实付守恒。社区版尚无营销时先把金额接口边界留好，不必立即建设复杂活动引擎。

## 6. 运行与交付验证

### A10 缺少统一健康与恢复视图

**依据**：[消息维护 Worker](../../backend/app/process/MessageDeliveryWorker.php) 失败只输出通用警告；交易事件当前无消费运行时；维护任务有状态但没有全系统统一健康入口。

**建议**：保留 HTTP `request_id`，进一步关联订单、单元、任务、事件和安全外部请求标识。建立 HTTP 进程、队列消费者、补投 Worker、维护 Worker 的心跳，以及积压量、最老任务年龄、过期租约、未知结果、失败原因、数据库/Redis 依赖状态。日志不记录验证码、密钥、正文或完整收件地址。

监控阈值按测量设置，不能把 Redis 可连接当作消费者正常，也不能把队列已 ACK 当作资源已交付。人工恢复入口受权限和审计保护，不提供任意重发未知结果。

**验收**：停止消费者、断开 Redis、过期租约和维护失败均可定位；通过一台实例可追踪交易至交付；敏感数据不进入诊断输出。

### A11 CI 不是完整发布门禁

**依据**：当前工作流仅 [api-documentation.yml](../../.github/workflows/api-documentation.yml)，主要执行契约和少量相关测试。仓库存在的 MySQL/浏览器测试不表示都会在 CI 执行。

**建议**：分成快速 PR 检查与发行检查：

- PR：语法、关键单元、OpenAPI、权限、受影响模块集成和前端构建。
- 交易变更：隔离 MySQL 的事务、金额、锁顺序、并发付款/取消、退款/开票额度竞争。
- 插件变更：全部交付适配器在同一进程加载、锁文件一致、网络替身协议测试。
- 发行：干净安装、迁移、插件依赖、完整产物、真实账号浏览器最小闭环和更新恢复。

**验收**：不是只统计测试总数；覆盖关键故障与并发。明确区分 SQLite、MySQL、模拟网络、真实外部平台和生产证据；无外部凭据时对应验收保持未完成。

### A12 Composer 不形成插件隔离

**依据**：[PluginDependencyLoader](../../backend/app/modules/plugin/infrastructure/PluginDependencyLoader.php) 已核对锁文件、拒绝同名依赖不同版本；核心 Easy SDK 与插件本地依赖并存。

**建议**：继续允许插件独立依赖，维护发行兼容矩阵和全插件同进程加载检查，报告冲突涉及的包与版本。宿主公共 HTTP 保留稳定快捷接口，SDK 由适配器决定。确有不可协调依赖时采用依赖前缀重写或独立服务，不默认把所有依赖搬到主 Composer，也不移除已有冲突检查。

**验收**：加载顺序不影响结果；冲突在发行或安装前被明确拒绝；任何交付插件都不缺 vendor；更新后 Worker 统一重启。

## 7. 会话、密钥与升级恢复

### A13 注销与撤销语义不一致

**依据**：[管理员退出](../../backend/app/modules/admin/auth/controller/AuthController.php) 和 [会员退出](../../backend/app/modules/member/controller/MemberAuthController.php) 清 Cookie；鉴权会重新核对账号状态和密码证明，但没有独立会话撤销记录。

**影响**：退出浏览器不等于使已复制令牌在服务端失效。账号禁用和修改密码已有失效机制，不能据此说所有旧会话都永远有效。

**建议**：先确定是否需要“本会话退出”“全部设备退出”“管理员强制退出”。需要时增加会话标识及服务端撤销/版本检查，令牌不携带秘密密码摘要；会员当前密码哈希摘要可改为独立会话版本或带密钥证明，与管理员证明策略统一。

**验收**：退出后的令牌重放按既定策略失败；其他设备是否保留有明确规则；改密/禁用立即生效；过期撤销记录可清理。该项需要专门验证，不在本报告中宣称漏洞已复现。

### A14 密钥轮换缺少版本化方案

**依据**：[SodiumSensitiveDataCipher](../../backend/app/shared/infrastructure/SodiumSensitiveDataCipher.php) 从 `APP_KEY` 派生密钥，密文保存随机 nonce 与密文，但没有显式 `key_id`。

**影响**：直接替换 APP_KEY 可能导致旧密文和部分摘要无法解读，也可能改变自动派生的 Redis 队列前缀。数据库恢复若丢失密钥和私有安装身份，不能视为完整恢复。

**建议**：新密文使用版本化信封和密钥编号；保留受控旧密钥解密与逐批迁移，写入只用当前密钥。把会话签名、业务加密、摘要和队列身份的职责区分，密钥轮换显式排空或迁移任务，防止任务留在旧队列前缀。

**验收**：轮换前后凭据和历史任务可读；队列不丢任务；旧密钥退役有核对步骤；备份恢复同时验证数据库、密钥、私有文件和安装身份。禁止把密钥写进本报告或版本库。

### A15 升级是单节点流程

**依据**：[LocalReleaseInstaller](../../backend/app/modules/software_maintenance/infrastructure/LocalReleaseInstaller.php) 使用本机维护文件、备份和文件恢复；[RunInstallationJobService](../../backend/app/modules/software_maintenance/application/RunInstallationJobService.php) 在危险阶段中断时标记 `recovery_required`。

**建议**：社区版先明确单节点部署，完成迁移失败、文件恢复失败、Worker 重启失败和私有文件丢失的恢复手册与演练。数据库迁移失败不可承诺自动回滚；恢复需协调数据库、代码、任务和外部已完成事实。

多节点需求出现后，再设计共享维护状态、发布编排、Worker 排空与版本一致性；本机 flock 不解决另一台机器同时升级。迁移仍使用前向版本，不修改已执行版本。

**验收**：故障注入后能恢复已付款订单及待任务，没有重复外部动作；恢复时间有实测；多节点未验收前不写进产品承诺。

## 8. 规模与商业版本边界

### A16 同步验证码请求需测量容量

**依据**：[SendRegistrationCodeService](../../backend/app/modules/member/application/SendRegistrationCodeService.php) 在 HTTP 用例中同步调用通道运输。

**建议**：先测厂商延迟、限流和 Worker 饱和度，限制发送时间预算，必要时独立发送 Worker 或采用返回挑战后查询状态的专用流程。验证码保留短时有效、单次消费与未知结果处理，不直接塞入可长期重试的普通通知队列。

**验收**：慢平台不会长期占满登录/注册 HTTP 容量；明确处理“平台受理但响应丢失”；未确定成功的挑战不激活。当前没有压测数据，不把同步发送本身写成已发生性能故障。

### A17 经营分析保持真实口径

**依据**：[聚合查询](../../backend/app/modules/business_analysis/infrastructure/DatabaseBusinessAnalysisRepository.php) 从订单、已完成退款与会员实时读取；[统计说明](../development/business-analysis.md) 限制查询范围并说明当前状态口径。

**建议**：现阶段保留有界查询和索引，不急于新建数据仓库。慢查询出现后再做每日汇总和重建机制；历史状态分析需要事件投影，利润需要供应成本与费用事实，不能用售价推算。多币种和分期支付真正开放时同步变更统计口径。

**验收**：日报可回算核对；退款不抹掉原付款；多实例不重复累计；新增成本事实前不展示“利润”。

### A18 商业能力目录仍粗粒度

**依据**：[official_platform.php](../../backend/config/official_platform.php) 目前只有 `commercial.professional/commercial.enterprise`；[ManageLicenseService](../../backend/app/modules/licensing/application/ManageLicenseService.php) 已做证书、期限与功能检查。

**建议**：保留社区版核心交易闭环；按实际商业功能登记稳定能力码，例如按量计费、密钥登录、CRM 高级能力。每项业务同时检查角色权限、商业权益与运行依赖，返回可解释的能力结果。未安装的功能不能因为证书通过就变成可用；到期保留历史数据和已有资源，限制新增高级操作的政策需明确。

**验收**：前端展示与后端拒绝一致；权限不能代替授权；证书不能替代插件安装；授权过期不删除客户和财务历史。

## 9. 推荐新增的后端结构

以下为建议，**本次不创建表或路由**。名称和字段应在对应功能落地时确认契约、索引、中文 COMMENT 和迁移。

| 建议结构 | 核心字段/约束 | 用途 |
| --- | --- | --- |
| `fulfillment_tasks` | 单元、操作、事件、请求键、供应绑定快照、外部标识、状态、租约；业务操作幂等唯一键 | 单实例开通/续费/终止任务 |
| `fulfillment_attempts` | 任务、尝试序号、起止时间、安全错误、结果；不存秘密报文 | 可审计尝试与故障恢复 |
| 交易事件消费记录 | 事件、消费者、状态、次数、下次执行、租约；事件与消费者唯一 | 对现有 Outbox 增加实际消费治理 |
| 支付/退款尝试补充 | 业务、商户、通道版本、金额币种、幂等键、厂商标识与未知结果 | 在线资金结果恢复；先复用现有支付通知/交易/退款尝试表 |
| 第三方身份关联 | 提供者、身份作用域、稳定外部身份、会员、验证时间；组合唯一键 | 账号绑定与可靠 OAuth 登录 |
| 会话与通用挑战结构 | 场景、账号摘要、浏览器摘要、失效与消费；会话版本/撤销 | 登录、找回与会话管理；复用注册基础而不混用挑战 |
| 优惠金额归属明细 | 订单项/单元/分项、优惠来源、优惠金额、分摊规则与快照 | 未来营销与退款金额解释 |

接口建设也按用例开放：单台履约查询/重试、支付创建/查单/回调、能力读取、第三方关联、会话撤销等。外部回调的鉴权是平台协议验签，不照搬管理员 Cookie 中间件；通用内部接口仍按已认证角色和数据归属校验。

## 10. 社区版实施顺序

### 阶段一 修复交付事实

处理 A01、A05、A06 的关键接口、A07、A10 的最小监控、A11 的核心门禁。目标是安装可用、已展示能力真实、接口能正确接入。暂不新增商业复杂功能。

### 阶段二 完成一条可恢复交易链

处理 A02、A03；若同时开放线上支付则处理 A04。先只覆盖云服务器、包年包月、固定带宽、密码登录、已选供应商。优先验证单台，再验证多台部分失败和单台退款。

完成标志：创建订单 → 付款 → 实例独立交付 → 真实服务 → 异常恢复 → 单台终止/退款，各步骤事实可核对。

### 阶段三 完成服务生命周期

续费建立新订单引用旧服务，上游确认后更新有效期；终止有供应释放确认；建立到期处理、明确授权的余额续费和库存生命周期。同步整理 A08、A12–A15。

### 阶段四 依据需求扩展

再建设其他产品类型、配置级营销、多渠道支付对账、精细经营分析和商业能力目录。A09、A16–A18 按业务开放条件实施，不让社区版配置界面承担所有未来商业策略。

## 11. 应保留的设计与应避免的重构

- 保留模块化单体；现阶段拆微服务会增加资金与库存一致性成本。
- 保留订单＋订单项＋实例单元；实例独立交付不要求每台建立销售子订单。
- 保留整数分、原资金来源、不可变流水、稳定分摊和交易快照。
- 保留消息数据库事实、Redis 唤醒、租约和未知结果保护。
- 保留插件本地依赖与受控 SDK，明确受信代码边界。
- 内部未上线 API 按最新契约更新；业务历史、已执行迁移和供应协议不能当作无用兼容删除。
- 不先建设全量商业策略、数据仓库、多节点热更新或任意插件执行沙箱，优先完成真实社区版购买与恢复。
