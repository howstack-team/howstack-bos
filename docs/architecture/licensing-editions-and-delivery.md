# 授权与版本功能隔离及升级下发技术方案

更新日期：2026-10-13  
适用项目：皓量云擎云业务运营系统 `howstack-bos`  
状态：授权权益与到期策略第一阶段已在本机实现；商业扩展与升级下发仍为后续设计。正式官网签发需同步最新权益契约。

第一阶段交付范围：本机签名 grants 校验、统一操作决策、使用与更新期限分离、有限离线租约、修订防重放、可信时间检查、绑定业务范围的加密受理证明、后台能力 Provider 和逐项权益展示。当前生产商业能力目录为空，基础社区功能不加收费门槛；未实现商业模块、业务额度占用及发行组合安装。实施细节见 [官网接入实施说明](../development/official-platform-implementation.md)。

## 方案结论

采用同一套核心、细粒度授权权益和独立商业扩展。社区版直接运行，专业版和企业版通过签名授权及经过审核的商业包增加能力。升级沿用本机维护任务，交付 PHP 代码、锁定的生产依赖和预编译前端资源，客户服务器无需 Node.js 编译。

第一阶段只建设统一权益决策、到期操作策略和一个高级经营分析扩展，验证授权、安装、权限、页面、迁移及恢复的完整链路。订单、资金、会员、基础产品和履约继续内置，保留当前模块化单体及目录，不拆成多套系统或大量 Composer 包。

业务连续性按操作定义：基础业务始终保留；已受理义务继续完成；新增高级操作按当前权益判断。到期不删除数据、不自动卸载模块，也不允许任意已有规则无限处理新增高级业务。

## 一 目标与范围

### 业务目标

- 社区版部署后，可以原地升级专业版或企业版，保留会员、订单、资金、实例和客户配置。
- 版本作为销售套餐名称，实际能力来自套餐、单独购买、试用或赠送形成的权益。
- 授权服务短时故障不影响已验证期限内的业务；真实到期与联网失败分别处理。
- 平台客户的终端会员可以继续登录、查看、管理存量服务和办理必要的账务收尾。
- 所有受保护操作同时满足功能权益、管理员权限或执行主体权限、对象归属及业务状态约束。

### 第一阶段边界

建设后台授权投影、受控商业扩展和整包升级。暂不建设微前端、Module Federation、任意第三方动态页面加载、远程命令执行、多节点自动滚动升级或通用商业模块平台。

多语言不在范围内。现有社区能力不因引入授权基础设施自动变成收费能力。最终套餐内容、价格、续费规则、试用政策和闭源交付条件另行形成正式商业条款。

## 三 统一概念与判断顺序

| 概念 | 含义 | 权威来源 |
| --- | --- | --- |
| Edition | 社区版、专业版、企业版等销售套餐名称 | 官网产品目录；本机展示已签名名称 |
| Capability | 稳定的功能标识，例如 `analytics.advanced` | Core 能力目录或经过审核的扩展目录 |
| Entitlement | 客户对能力的使用、更新和额度权益 | 官网权益账本及签名证书 |
| Installation | 授权绑定的一个部署实例 | 本机持久安装身份及官网激活记录 |
| Module | 实际交付的商业代码包 | 已审核文件、安装记录与运行注册 |
| Permission | 某个管理员或执行主体可以进行的动作 | 本机 RBAC 或固定系统任务权限 |
| Decision | 某项具体操作现在能否执行及原因 | 本机统一策略，根据上述事实计算 |

功能访问依次核实执行主体、公开操作入口、模块安装与兼容状态、必要的权益、权限及对象归属，最后进入业务状态和事务校验。接口不得在未认证时暴露授权详情。

纯 Core 社区功能不要求商业证书。依赖商业模块的功能必须有实际可运行的包；具有授权但未安装的功能返回“待安装”，不能在 Bootstrap 中假装可用。

版本名不直接参与业务 `if` 判断。上层统一询问具体能力及操作，套餐到能力的组合由官网维护。客户端未知能力不能因证书声明而获得路由或执行权限。

## 四 核心与商业代码边界

### 保留当前目录

```text
backend/
├── app/
│   ├── modules/
│   │   ├── licensing/              授权查询与权益决策
│   │   ├── official_platform/      官网连接、实例身份、签名验证
│   │   ├── software_maintenance/   下载、备份、安装和恢复
│   │   ├── plugin/                 宿主扩展注册与生命周期
│   │   └── ...                     订单、资金、会员、产品等内置模块
│   └── shared/
│       ├── contract/               跨模块权益决策接口
│       └── plugin/                 已开放 SDK 与 DTO
├── plugins/
│   ├── provider/                   现有供应适配器
│   ├── sms/                       现有短信适配器
│   ├── mail/                      现有邮件适配器

│       └── advanced_analytics/    规划中的首个官方商业扩展

        └── console/
            ├── pc/
            └── mobile/            可选独立移动端
```

上图的 `feature/advanced_analytics` 为目标目录，不表示当前已实现。扩展入口直接位于包根目录，不恢复 `api/` 分层，不为无配置、无前端或无自有数据的包创建空目录。

### 代码分发

公共仓库保存社区 Core、稳定 SDK、能力目录、公共安装器及社区前端。商业业务实现放在私有仓库，CI 在明确的构建清单下组合发行；社区包要执行商业源码和资源排除检查。

后台可共用页面框架和通用组件。首个独立商业页面源码随私有扩展维护，在官方 CI 中静态编入商业发行组合的后台 Dist。客户无需现场编译，也不存在浏览器动态执行清单里的任意 JS 地址。

独立商业模块不修改核心资金表、不替换付款用例，不用万能 Hook 接管所有流程。优先开放只读查询、明确的策略接口和固定任务接口；写入通过公开应用命令。

原生 PHP 与同域前端都是受信代码。包签名证明来源与完整性，SDK 约束表达开发边界，二者都不构成恶意代码沙箱。

## 五 能力目录与统一决策

### 能力目录

能力目录由代码维护，记录标识、依赖模块、允许的操作、到期策略及所需权限。商业证书只授予权益，不得远程指定 PHP 类名、处理器、数据库表名、路由、Shell 命令或宽松的到期策略。

第一阶段只注册实际交付的 `analytics.advanced`。`provider.multi`、`finance.auto_reconciliation`、`iam.sso` 等可列入产品路线，但在业务实现及到期策略完成前不向客户显示“已可用”。

### 接口职责

演进现有 `CommercialFeatureGateInterface`，提供两种操作：

- `decide(capability, operation, context)`：返回不可变决策 DTO，用于页面投影与业务预检。
- `require(capability, operation, context)`：不满足条件时抛出统一业务异常，用于执行入口。

决策 DTO 至少包含 `allowed`、`reason`、`entitlement_status`、`use_until`、`updates_until` 和 `entitlement_revision`。上下文只允许已定义字段，例如执行主体、业务引用、配置版本、受理时间和额度占用引用；业务引用必须由宿主读取核实。

改造时搜索并统一替换现有调用，当前未上线阶段更新现行契约，不长期维护两套授权入口。具体类名和 DTO 以实施时的契约审查为准。

### 操作分类

| 操作 | 用途 | 到期规则 |
| --- | --- | --- |
| `read_existing` | 读取曾生成的报告、配置或历史记录 | 有历史使用范围且满足 RBAC 时继续 |
| `configure` | 新建配置、增大范围、启用高级规则 | 需要有效权益 |
| `start_new` | 产生新报告、发起新的高级调度或自动化 | 需要有效权益及必要额度 |
| `complete_existing` | 完成此前有效受理的固定任务与补偿 | 校验原业务范围后继续 |
| `maintain_existing` | 存量服务必要管理与收尾 | 由业务目录明确允许，不能顺带扩容 |
| `download_update` | 获取商业模块的新版本 | 校验更新权益、下载资格和兼容性 |

核心退款、支付通知处理、账务收尾和基础会员登录不依赖商业能力，不能因为权益失效被全局拦截。到期后的读取也不能变成运行新高级查询的入口，例如“查看历史报告”只读取已生成结果。

### 执行入口

HTTP Controller 负责参数与身份边界，Application 用例执行权益检查。队列消费者、CLI 和定时任务调用同一决策接口，使用明确系统主体和业务引用。无需在每个领域实体重复检查，也不能只在菜单或中间件检查。

受理与执行分别检查：新的高级任务在受理时必须有有效权益；稍后执行时可以按 `complete_existing` 完成该任务。循环自动化每产生一项新业务都属于 `start_new`，不能沿用创建规则时的一次授权无限执行。

额度由所属业务模块在事务中原子占用和释放，使用稳定幂等标识。签名额度决定上限，当前用量来自本机事实；超额后保留存量并阻止增加，不强制删除。第一阶段不引入没有具体业务含义的通用计量平台。

## 六 授权证书与期限

### 权益签发

官网将套餐、单买、试用及赠送汇总为实例权益。相同能力多个来源的有效范围按已发布的产品规则合并，不默认累加额度；例如取最大并发额度和较晚有效期限，若允许额度叠加须明确定义。

沿用 `kid`、`payload`、`signature` 信封及原始载荷字节验签。下面仅展示目标载荷结构，不是当前接口响应；正式契约需同步更新官网和本机。

```json
{
  "schema_version": 1,
  "type": "software-license",
  "software_code": "howstack-bos",
  "license_no": "LIC-EXAMPLE",
  "installation_id": "00000000-0000-4000-8000-000000000001",
  "connection_id": "00000000-0000-4000-8000-000000000002",
  "edition": "professional",
  "edition_name": "专业版",
  "status": "active",
  "revision": 12,
  "issued_at": 1791849600,
  "offline_policy": "online_lease",
  "offline_until": 1792454400,
  "grants": [
    {
      "capability": "analytics.advanced",
      "use_until": 1823385600,
      "updates_until": 1823385600,
      "limits": {}
    }
  ]
}
```

示例标识及 Unix 秒值只说明类型，不对应真实授权。每项权益独立保存 `use_until` 和 `updates_until`，支持单独续期。`use_until=null` 只表达签发方明确授予永久使用；`updates_until=null` 表达明确授予永久更新，不能由缺失字段推断。

证书的 `offline_until` 表达授权刷新租约，不替代任何能力的使用期限。在线授权必须有有限租约；独立离线授权必须通过签名 `offline_policy` 明确声明允许不联网，不能通过把普通证书的日期改成 null 实现。

目标结构不再由客户端版本映射决定商业权益。当前 `expires_at` 和版本功能映射的消费端需统一改造；官网 v1 证书字段按协调发布更新，不在业务内部新增旧字段别名。已有客户端若已分发给外部实例，则在正式切换前另定协议升级与重新签发安排。

### 期限与刷新建议

| 项目 | 第一阶段建议 |
| --- | --- |
| 普通在线授权刷新 | 沿用约 6 小时周期，增加实例错峰；接近截止时提前刷新 |
| 网络失败重试 | 至少间隔 15 分钟，记录失败但不清空证书 |
| 普通离线租约 | 建议签发 7 天；续费不会由本机自行延长租约 |
| 付费使用截止 | 各能力分别判断，以签名权益时间为准 |
| 更新资格 | 按模块版本首次发布时间与更新期限判断，并仍校验官方下载权益 |
| 独立离线授权 | 后续企业能力；通过受控导入的签名证书实现，不在首期默认开放 |

更新服务到期后，已获得的许可版本仍按原使用权益运行。官网应允许重新获取客户原有版本的可验证包用于灾难恢复；该资格不等同于获取更新截止之后的新版本。

### 验签与状态保护

- 公钥按 `kid` 预置并受更新保护；未知 key 拒绝。轮换先建立由既有信任证明的新信任，不能直接信任远程响应携带的公钥。
- 校验软件、载荷类型、实例和当前授权连接；绑定身份持久化，域名和 IP 作为辅助条件，不能导致普通内网或换 IP 部署突然失效。
- 限制载荷字节数、JSON 深度、权益数量、标识长度和额度取值；未知能力不授予执行权。
- 持久化最高已接受修订号及证书摘要。更低修订拒绝；同修订只允许相同载荷。证书刷新时仍核对签发时间及租约。
- 官网发现撤销或减少权益时必须提高修订号；本机收到明确、有效的撤销后不能回退到旧缓存证书。
- 安装身份、证书、连接令牌与信任状态使用既有私有卷及加密状态；浏览器和普通审计只得到脱敏投影。
- 维护可信最近时间，检测明显系统时间回退；异常时限制新高级操作并提示修复，存量收尾仍按业务证明执行。拥有主机最高权限者仍可篡改程序或恢复旧状态，本方案不承诺绝对防破解。

验签使用 PHP Sodium 提供的 Ed25519 验证方法，私钥只存在于签发平台。[PHP 官方验签文档](https://www.php.net/manual/en/function.sodium-crypto-sign-verify-detached.php)

## 七 到期与业务连续性

### 状态与行为

| 状态 | 新高级操作 | 既有义务 | 基础业务 |
| --- | --- | --- | --- |
| 有效证书且使用期限内 | 允许，仍校验模块、RBAC 和额度 | 继续 | 继续 |
| 刷新失败但离线租约有效 | 按本地已验证权益允许 | 继续 | 继续 |
| 使用到期或试用到期 | 限制；允许历史读取及必要收尾 | 继续已有效受理任务 | 继续 |
| 离线租约结束 | 暂停新增高级办理，联网重新核验 | 按原业务证明继续 | 继续 |
| 已收到签名撤销 | 阻止新增高级办理，不使用旧证书解锁 | 合法存量收尾继续；安全事件另行处置 | 继续 |
| 证书损坏、签名无效或实例不匹配 | 拒绝授予商业权益 | 只根据独立、未损坏的既有业务证明处理 | 继续 |
| 模块文件损坏或不兼容 | 阻止相关操作并告警 | 保留任务，进入修复流程，不假装执行成功 | 不受影响的 Core 继续 |

“暂停新增”不能自动写入插件 `disabled` 状态；授权与运行状态分开。模块正常加载才能完成允许的存量任务。文件故障则无法保证其执行，应保留业务记录、提供修复路径。

### 原业务证明

涉及存量业务的高级能力须在有效受理时，随业务事务保存宿主生成的执行范围，包括业务 ID、能力、权益修订、策略版本、受理时间、配置摘要及原始授权证明引用。证书或证明引用应加密保存或通过受控完整性保护，禁止直接使用客户端传来的 `accepted_at` 或 `grandfathered=true`。

保存原始证明时同时保留已验签载荷或可核验的不可变引用，不能只保存一个无法还原的摘要。证明限定已经受理的对象、动作和幂等标识；增加实例、延长期限、扩大调度范围均需重新核实权益。证明不会免除 RBAC、对象归属、可退款金额、库存和幂等校验。

退款和已支付履约原则上继续；新的高级续费流程或新增采购重新判断。基础续费可以走 Core 支持的普通路径，但不得静默改变原实例供应绑定或价费规则。临界时刻采用同一次受理的授权判断与事务记录，支付成功后的必要履约不能因随后到期被取消。

### 不同商业能力的策略

| 能力示例 | 到期仍可执行 | 到期限制 |
| --- | --- | --- |
| 高级经营分析 | 查看、导出已生成报告；完成已受理的固定报告任务 | 新分析、定时任务新批次、新增高级报表配置 |
| 高级调度 | 已受理订单的开通、失败查询与补偿；存量实例必要维护 | 新高级调度订单、池扩容、新调度规则；需实现后再开放 |
| 自动对账 | 查看已生成结果；完成已受理的固定账期任务 | 新自动批次、新规则；核心付款通知、入账和退款继续 |
| SSO | 已有客户必要登录与受控管理员恢复入口，按正式策略保留 | 新身份源、新接入范围；必须提供可用的本地恢复方式后才能上线 |

该表是后续能力的设计约束，不代表这些模块已经实现。功能上线前必须给出明确策略，不能继承一个“所有任务永远继续”的默认值。

## 八 商业扩展接入

### 生命周期复用

沿用 `business_plugin_installations` 的 `installed/enabled/draining/disabled/uninstalled` 状态、修订锁及生命周期审计。保留原包版本和摘要，授权状态通过投影计算，不复制为另一套安装状态表。

新商业扩展安装并验收后，管理员有权限且具有有效权益时才启用。到期保留原启用意愿，运行能力由统一决策限制；续费后可恢复允许操作。管理员此前主动停用的扩展，续费不得自动启用。

### 最小包约定

复用 `plugins/feature/<plugin_id>/plugin.json`，新增必要的宿主识别字段及公开固定入口，避免另一套 `commercial.json/module.json`。继续使用既有版本、兼容要求、权限和迁移声明；简单能力从入口接口识别，只有需要运行前预检的元数据才写入清单。

首期只允许官方审核的 `feature` 包声明：稳定能力标识、固定后端入口、自有权限、已审核只读页面、受控迁移及数据保留策略。定义类别契约时，不放宽现有短信、邮件、支付和供应适配器的权限。

路由由宿主注册到 `/api/admin/v1/plugins/<plugin_id>/...`，不任意扫描包内全部控制器，不允许覆盖 Core 路由。权限码采用 `admin.plugins.<plugin_id>.<action>`，注册后能在角色权限分配中选择。新权限默认不赋予普通角色；按现有超级管理员规则处理，不能绕过角色体系。

菜单以稳定页面键与父级键挂载，冲突拒绝。第一阶段前端路由与页面在 CI 静态编译，后端仅返回允许的页面键；清单不下发可执行组件代码。

### 数据迁移

首个扩展的审核后迁移随整体发行包放入宿主 `database/migrations/`，由现有 `system:migrate` 统一执行，文件名前缀和类名全局唯一。包清单声明预期迁移集合与摘要，不能另写启动自动建表路径。

扩展自有表使用 `ext_<plugin_id>_<purpose>` 无前缀逻辑名，部署前缀仍由系统配置添加。所有表、主键和字段设置中文 COMMENT，明确时间、金额、状态、引用及敏感数据用途。只允许新增自有表和经审查的变更，不修改其他模块的表。

既有迁移不可改写或删除。卸载及授权到期不运行 `down()`。后续若支持独立插件包迁移，再增加按插件记录的迁移账本和调度器，第一阶段不另造一套迁移系统。

依赖在 CI 按锁文件构建，完整交付生产依赖；禁止客户现场 Composer 脚本或 NPM 安装。共享 PHP 类或 SDK 冲突必须在发布前及本机预检时拒绝。

## 九 本机数据与审计设计

| 数据 | 复用或新增方式 | 主要内容 |
| --- | --- | --- |
| 官网授权私有状态 | 复用 `official_platform_state` 加密载荷 | 原证书、权益修订、证书摘要、最近验证时间、可信最近时间和安全错误 |
| 插件安装事实 | 复用 `business_plugin_installations` | 包 ID、类别、版本、摘要、运行意愿与修订 |
| 生命周期审计 | 复用 `business_plugin_events` | 安装、启停、升级、操作者、IP 和地点快照 |
| 安装任务 | 扩展 `software_installation_jobs`，新增前向迁移 | 发布组合 ID、源组合 ID、计划摘要、安装进度与失败阶段；仍保存已批准清单 |
| 当前发布组合 | 第一阶段在私有状态保存受控部署记录 | 发布 ID、Core 版本、模块版本与摘要、前端 Build ID、迁移目标 |
| 历史使用证明 | 首个分析扩展自己的任务与结果表；未来业务优先复用政策快照 | 受理范围、原权益证明引用、原策略版本、结果与幂等标识 |
| 授权变更审计 | 复用管理员操作日志；系统刷新记录单独的安全投影 | 原因、修订、能力摘要和时间，不含原始证书、令牌或密钥 |

不在本机复制官网套餐订单或支付账本。权益证书是授权事实，业务表保存运行事实。加密私有状态的新增键无需为每个权益建一张表，需定义明确结构、大小限制和并发修订规则。

新数据库字段和索引只在具体用例确定后添加，金额和额度使用整数。所有 Schema 变更通过前向迁移；首次安装、已有数据升级、自定义表前缀和失败恢复都需验证。

审计必须携带 `request_id`、操作者及用户操作发生时的 `client_ip/client_ip_location`；系统定时任务二者为 null。浏览器只能获取脱敏授权状态、任务进度和备份引用，不能获取服务器私有路径。

## 十 前端与接口契约

### 扩展既有接口

保留现有后台入口：

- `GET /api/admin/v1/official-platform/license`：展示购买版本、验证状态、期限与权益摘要。
- `POST /api/admin/v1/official-platform/license/refresh`：由有权限的管理员主动刷新。
- `GET /api/admin/v1/system-updates`：查看可安装发布和本机任务。
- `POST /api/admin/v1/system-updates/check`：检查兼容发行组合。

系统更新受理接口与任务查询继续沿用现有控制器约定，实施时加入固定的发布组合标识、计划摘要和幂等键。版本升级复用授权与更新页面，应用中心继续承担插件生命周期管理，不新增三套管理入口。

后台 Bootstrap 在已有契约中增加 `capabilities` 和 `release_id`；若授权决策改变，返回新的权益修订和投影。PC、移动会员中心和官网仅接收相关业务的操作结果，公开接口不得暴露授权编号、全部商业目录或账户连接详情。

以下是规划中的 Bootstrap `data` 片段，完整 API 仍使用 `code/message/data/request_id` 和 `X-Request-Id`：

```json
{
  "release_id": "release-example-001",
  "capabilities": {
    "analytics.advanced": {
      "installed": true,
      "status": "active",
      "operations": {
        "read_existing": true,
        "configure": true,
        "start_new": true
      }
    }
  },
  "entitlement_revision": 12
}
```

### 页面行为

前端提供 `useCapabilities()` 和页面守卫，统一消费后端投影。权限缺失直接隐藏操作；已购买但未安装显示“待安装”；到期显示原因并保留历史入口；模块不兼容显示需修复状态。

页面加载、刷新授权、安装完成和接口明确返回授权状态变化后重新读取投影。期限到达时主动刷新本机投影，避免按钮一直停留在登录时状态。按钮状态不能代替服务端执行前检查。

错误使用现有统一响应。业务错误原因区分未安装、授权到期、离线核验到期、明确撤销、额度超限、模块不兼容和安装维护中；具体五位业务码在 Contract 实施时分配，不在文档中占用未经核查的编号。

当前后台 React 18、会员控制台 React 19 是独立构建，不能假设共用一个动态 React 运行时。自定义会员主题通过稳定 API 适配新功能；系统更新不替换客户所选主题，也不承诺第三方主题自动获得新增商业页面。

API 唯一源仍是 `contracts/openapi/`。实现时同步官网签发契约、本机客户端、Bootstrap、前端消费者和测试；每个新页面同时注册访问与操作权限。

## 十一 发行组合与安装计划

### 区分软件版本与安装组合

同一个 Core 版本可以有不同的安装组合。版本升级不能仅凭 `target_version > current_version` 判断，否则社区版与专业版都使用同一 Core 版本时无法安装扩展。

新增不可变 `release_id` 和组合摘要，描述 Core、模块、前端及迁移目标。现有严格版本递增规则继续用于普通 Core 更新；同 Core 的商业升级通过明确的升级动作和不同组合 ID 校验，不能简单取消所有版本检查。

组合 ID 本身不表示先后顺序。签名计划增加发布序号及明确的源组合条件，本机保存已确认的发布序号和模块版本；默认拒绝旧组合重放、组件版本倒退和来源不匹配。灾难恢复通过独立受控恢复流程处理，不借普通更新入口绕过这些规则。

安装计划至少包含：源 Core 与源组合、目标 Core 与目标组合、增补或更新模块、前端 Build ID、迁移集合、最低 PHP/数据库/扩展要求、包字节数、SHA-256、发布时间和管理员批准的计划摘要。

单独绑定一个下载包不够：上述组合信息必须被签名覆盖，内部发布清单与外层计划一致。使用权益与下载授权再次核对后才能修改运行文件；若在执行前撤销或到期而已不满足该安装动作的规则，停止安装并保留原部署。已经开始迁移的任务则按恢复状态处理，不能中途删除商业文件或强行退回社区组合。

管理员确认后，任务执行前重新取得短期签名清单，核对安装计划和包身份。新的签发时间与下载凭据允许变化，目标内容及批准范围不能变化；变化后要求重新查看并确认，不静默安装另一组合。

### 第一阶段交付方式

官网根据客户当前已安装模块和有效下载权益选择经过 CI 测试的整体发行组合。每个组合包含：

```text
经过批准的 Core 文件
+ 本次允许安装或升级的官方商业模块
+ 匹配组合的后台 Dist
+ 必要的默认主题资源
+ 受控前向迁移
+ 文件与版本清单
```

CI 可以复用模块构建产物，但本机第一阶段按一个任务安装一个组合，不做多个包并发落盘。组合清单应保留既有已安装商业模块的明确版本，不能因为订阅到期把文件移除。若新 Core 与过期模块无兼容版本，拒绝该升级并说明原因，不能更新后让存量模块失效。

社区包、专业组合、企业组合是构建产物，代码仍共用 Core。单独购买、试用等组合按实际支持范围提供；初期只发布有限、经过测试的组合，不向客户开放任意依赖求解。

后续再扩展独立商业 Addon 的下载安装。整包安装支持的升级计划不能依赖当前只接受 provider 的应用安装器冒充完成；签名协议、路径白名单和插件注册必须一起扩展。

### 社区升级体验

沿用当前官网账号连接确认流程，在官网购买、选择或续费权益。本机刷新后展示已购买但待安装的能力及兼容发行组合，由具有更新权限的管理员确认安装。连接成功或浏览器回跳 URL 不能授予能力。

已安装兼容模块续费只刷新权益，不强制重新下载代码。更新期限到期不删除当前版本；需要更新时按新发行的兼容组合办理。

## 十二 安装步骤与运行一致性

1. **受理计划**：认证与权限检查、验证签名和来源组合，绑定任务 UUID、计划摘要及安装互斥。重复同一请求返回同任务，不同目标复用 UUID 返回冲突。
2. **下载到私有暂存目录**：限制域名、跳转、大小、超时和 HTTPS；不把官网凭据转发给对象存储。校验外层包和清单中的文件摘要、路径与文件集合。
3. **完整预检**：检查环境、空间、依赖冲突、已安装模块及历史迁移，拒绝自定义配置覆盖和未经管理的同名目录。校验后台与默认主题资源属于同一兼容组合。
4. **进入维护并排空**：阻止新的业务受理，暂停有关队列领取；已运行任务到达安全检查点。排空超时则在替换前退出并报告，不能把固定等待 10 秒视为排空证明。
5. **处理回调窗口**：支付回调与外部通知必须有已实现的原文持久化、幂等和事后处理机制才能承诺接收；否则返回符合厂商重试规则的临时失败，明确维护窗口。不能丢弃回调后返回成功。
6. **一致性备份**：写入者停止后备份数据库、受影响文件、安装记录和当前组合。已在用的身份及私有配置保护不变，备份权限与私有卷持久化保持现有规则。
7. **安装代码和资源**：按批准文件集合写入，记录文件恢复日志；只允许安装清单列出的官方商业目录。禁止覆盖 `.env`、APP_KEY、数据库配置、官网信任配置、客户插件、上传、所选主题配置及私有身份。
8. **执行前向迁移**：使用新的独立 PHP 进程调用宿主受控迁移入口，核对目标迁移账本；不执行包携带的任意命令或安装脚本。
9. **登记和完整重启**：迁移成功后登记目标包和组合；重启 HTTP、队列及维护进程，核对所有执行进程使用目标组合。OPcache 开启时按部署模式刷新，不能只修改磁盘后声称完成。
10. **健康确认**：验证 Core/模块版本、文件摘要、迁移目标、路由与权限注册、后台资源和必要默认主题资源可达。通过后解除维护、恢复任务并标记成功；官网回报失败只重试报告。

生产部署下，可将替换过程演进为版本目录及一次性切换，但当前安装器使用原位文件替换与恢复日志。首期在维护窗口内核对逐步状态，不把多文件替换描述成已经实现的原子发布。

默认官方主题的托管资源随组合更新，客户上传主题和当前选择保持不变。资源按内容摘要发布，更新过程中保留旧资源供已有页面使用，成功并经过保留期后再清理，避免旧页面 Chunk 404。

更新不等于不停机升级。首期单实例维护窗口需在确认页明确展示；集群和独立守护进程的协调升级以后再建设。

## 十三 失败恢复与降级

| 失败阶段 | 本机处理 | 再次执行规则 |
| --- | --- | --- |
| 授权、签名或兼容预检 | 拒绝，不变更运行代码 | 修正条件后创建新计划 |
| 下载或暂存校验 | 清理该任务暂存文件，保留审计 | 重新取有效清单，仍绑定批准目标 |
| 排空或备份失败 | 未替换文件时恢复原运行，记录失败 | 修复原因后重新受理 |
| 文件替换失败且尚未迁移 | 按完整日志恢复原文件及安装记录 | 恢复核实通过后才能退出维护 |
| 备份、恢复或文件状态未知 | 保持维护并标记 `recovery_required` | 人工核实，禁止自动重放 |
| 迁移开始后失败 | 保持维护、完整备份和目标诊断信息 | 前向修复或恢复匹配的数据库与代码，不直接切回旧代码 |
| 重启或健康确认失败 | 保持待重启或人工恢复状态 | 运维修复并重新确认，不重复迁移或扣除权益 |
| 官网结果回报失败 | 本机成功状态不回退 | 仅按任务 UUID 幂等重发回报 |

每次升级目标都必须提供一份恢复说明，包括备份验证、预期数据库状态和前向修复步骤。MySQL DDL 不能假设可以由应用事务整体回滚。数据库恢复与文件恢复必须配套，不能恢复一项后直接解除维护。

到期和用户主动降级优先表现为能力策略变化，保持已安装模块、数据及历史接口的安全读取。申请卸载须检查存量实例、未决资金、任务、依赖模块和历史结果；有必要执行引用时拒绝删除代码。无需在升级时人工搬迁业务数据，但允许并需要受控结构迁移。

## 十四 安全与发布许可边界

授权中心私钥与日常下载服务分离，下载资格、证书权益、包签名及本机 RBAC 各自验证。下载链接泄漏不能赋予功能，包已下载也不能替代有效授权。

更新防护需要覆盖过期元数据、旧版本重放、组合混搭、错误软件或实例、恶意路径和密钥轮换。参考 TUF 的元数据与信任更新原则，首期落实明确的签名和状态规则，不宣称已实现完整 TUF 协议。[TUF 官方规范](https://theupdateframework.github.io/specification/latest/)

企业离线模式需要接受撤销无法实时传播的事实，通过有限使用期限、人工更新证书或明确的永久许可条款解决。网络不可达不能被当作已收到撤销，签名无效也不能被解释成正常网络故障。

目前仓库采用 Apache-2.0。商业扩展的源码交付、SDK 许可、第三方贡献权属、依赖许可证与闭源发行兼容性须在首次商业发布前完成专门审查；使用私有仓库、PHP 加密或独立目录本身不能确定许可结论。本方案不变更现行开源协议，也不承诺已经具备闭源发行资格。

## 十五 第一阶段实施顺序

| 阶段 | 交付内容 | 通过条件 |
| --- | --- | --- |
| P0 统一契约 | 官网权益载荷、能力目录、操作策略、首个模块包约定及发行组合契约 | 当前代码与目标差距逐项明确；两端签发与消费约定一致 |
| P1 本地权益决策 | 演进 FeatureGate、期限与修订校验、私有状态、Bootstrap 和授权页 | 无授权社区正常；授权到期、断网和撤销行为分别通过测试 |
| P2 首个官方扩展 | `advanced_analytics` 固定入口、权限、历史报告表及页面 | 无插件、无权益、无权限分别拒绝；有权益但未安装显示待安装 |
| P3 升级组合 | 同 Core 商业升级、CI 构建、整包清单、商业路径预检和模块迁移 | 社区安装保留原数据，原地获得分析模块；配置和主题不被覆盖 |
| P4 生命周期与恢复 | 到期读取、续费恢复、排空、回调窗口、多进程健康确认及失败恢复 | 中断恢复演练和下表全部关键验收通过，再允许正式售卖 |

首个扩展建议选择高级经营分析，使用只读公开查询和自身报告结果，不参与订单报价、资金入账或资源生产。用它验证商业分发基础后，再逐个接入高级调度、自动对账与 SSO；每个新增能力都先制定业务连续性策略。

为避免只有接口和依赖而没有可用功能，P2 必须交付真实报表生成、历史读取、对应页面及权限分配，不能用空插件或假数据宣称链路完成。首期高级报表的具体指标另列业务需求。

## 十六 验收标准

| 验收场景 | 预期结果 |
| --- | --- |
| 社区版未连接官网 | 登录、基础下单、支付和存量管理不依赖商业联网 |
| 单买或赠送能力 | 套餐名不变仍可正确授予已实现能力；不解锁其他功能 |
| 有权益但缺少包 | 显示待安装，不能访问模块 API |
| 有包但没有权益 | 不能发起新高级操作，直接调用 API、CLI 或队列入口也不能绕过 |
| 有权益但缺少 RBAC | 菜单及操作按权限收敛，服务端返回明确拒绝 |
| 网络中断 | 租约内按本地权益运行；超出租约限制新高级操作，基础业务与合法收尾继续 |
| 有效签名撤销后重放旧证书 | 旧修订不能恢复能力；同修订不同载荷拒绝 |
| 时间回退或安装身份不匹配 | 不新增商业权益，明确告警，仍可进行已证明的必要收尾 |
| 高级分析到期 | 历史报告仍可读取和导出；新分析与定时新批次拒绝 |
| 续费但插件曾主动停用 | 权益恢复，插件不自动启用 |
| 到期前受理、到期后执行 | 原范围内任务幂等完成；新增对象或扩大范围拒绝 |
| 同版本社区升级专业 | 不依赖 SemVer 增长即可安装不同组合，旧组合重放与错误来源拒绝 |
| 更新期限结束 | 当前许可版本不被删除；新版本下载规则与旧包灾难恢复资格分别验证 |
| 更新 Core 而旧商业模块不兼容 | 预检拒绝，不生成破坏存量业务的组合 |
| 并发安装、断连与刷新授权 | 互斥及修订生效，不同时改运行文件或混用连接 |
| 自定义主题和客户配置 | 模板选择、配置、上传、密钥与客户插件在升级前后保持 |
| 回调恰逢升级窗口 | 不丢通知后假确认；重试或可靠持久化按既定协议验证 |
| 文件替换中断与迁移中断 | 各阶段按恢复表处理，完整备份可验证，禁止盲目重放 |
| 多进程重启后 | HTTP、队列及维护进程均报告目标组合，前端 Build 与 API 匹配 |
| 数据库全新安装与升级 | 自定义前缀、中文 COMMENT、历史数据、任务幂等和迁移账本正确 |
| 社区发行包检查 | 无商业实现、私钥、真实凭证或未许可依赖，包摘要与清单一致 |

静态检查、单元测试、模拟官网响应和临时目录升级只能验证各自范围。正式上线还需要真实官网签发与续费、正式包下载、本机同版本升级、真实数据库恢复和生产部署模式重启演练，不能用构建成功代替这些验收。
