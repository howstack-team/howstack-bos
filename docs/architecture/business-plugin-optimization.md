# 业务插件体系优化方案

## 1. 目标、状态与本轮范围

皓量云擎云业务运营系统采用独立的业务插件体系：**分类目录、声明式配置、固定能力接口、宿主统一编排**。让开发者集中实现外部接口或专项扩展，核心系统继续负责权限、订单、资金、服务状态和可靠执行。

本文是目录和插件逻辑整改的主方案。更新日期：2026-10-04。

| 状态 | 内容 |
| --- | --- |
| 当前实现 | 魔方云位于 `backend/plugins/provider/magic_cloud/`，使用统一 JSON、v1 DTO、受限 HTTP 服务与宿主安装记录；系统尚未上线，仅维护一套 v1 协议 |
| 当前实现 | 连接配置加密保存，私密字段不回显；创建资源供应商时选择对接平台，一个插件可以创建多个供应商连接 |
| 确定设计 | 本系统业务插件统一放入 `backend/plugins/<category>/<plugin_id>/`，由系统自己的注册器管理；目录整改完成后不保留空的 `backend/plugin/` |
| 确定设计 | 配置声明与配置值分开，按类别提供固定方法和版本化 DTO，通过受控宿主服务调用；同系统上下游继续作为核心模块 |
| 当前实现 | 分类加载、清单/配置校验、固定 SDK、应用中心安装管理、后端生命周期维护、连接配置、安装审计、引用保护及开发工具 |
| 后续建设 | 其他类别运行契约、真实生产、任务排空、插件迁移与包签名发布、动态前端扩展及进程隔离 |

**阶段一、二代码已落地**，实际协议见 [供应插件开发规范](../development/provider-adapters.md)。本次完成本地包登记及连接管理，不提供包上传、签名分发、多 Worker 热切换或真实资源生产。第三阶段仍按交易、任务与外部联调依赖建设。

## 2. 目录与插件分类

### 2.1 使用 `plugins/`，区分框架机制

业务插件根目录确定为 **`backend/plugins/`**，不放在仓库根部，也不放在 Webman 应用插件目录 `backend/plugin/`。它随 PHP 后端部署和安装包交付，前端只加载审核后的公开资源。

目标目录如下；每个类别只在存在实际插件时创建目录：

```text
backend/
├── app/
│   ├── modules/
│   │   ├── plugin/                插件注册、配置、安装与生命周期管理
│   │   ├── provider/              资源供应商、供应映射及对接编排
│   │   └── ...                    产品、订单、资金、上下游等核心业务
│   └── shared/
│       └── plugin/                稳定的公共 SDK 接口和 DTO
├── plugins/
│   ├── provider/                  外部资源提供者
│   │   ├── magic_cloud/
│   │   ├── proxmox_ve/
│   │   └── ...
│   ├── payment/                   支付渠道
│   ├── identity/                  实名认证渠道
│   ├── sms/                       短信渠道
│   ├── mail/                      邮件渠道
│   ├── storage/                   文件存储渠道
│   ├── oauth/                     第三方登录通道
│   ├── product/                   新产品业务定义扩展
│   └── feature/                   受控的专项功能扩展
├── config/plugin/                Webman Composer 组件配置，继续保留
├── vendor/                       Composer 依赖，继续由 Composer 管理
└── themes/                       官网主题，独立管理
```

这里需要区分三个路径：

| 路径 | 用途 | 整改方式 |
| --- | --- | --- |
| `backend/plugins/` | 本系统业务插件 | 建设自己的清单、加载器、配置和生命周期 |
| `backend/plugin/` | Webman 应用插件 | 当前只有已接入的业务供应插件；迁移并确认依赖后移除，本阶段不另建 Webman 应用插件 |
| `backend/config/plugin/` | Webman 基础组件的配置 | 保留数据库、队列、校验、事件等依赖所需配置，不随业务目录迁移删除 |

Webman 官方应用插件使用 `plugin/`，有自己的配置加载、路由和安装约定；本系统的 `plugins/` 属于自主加载方案，需要显式实现注册和启动接入，不能期待框架自动扫描。[Webman 应用插件文档](https://www.workerman.net/doc/webman/plugin/app.html)

### 2.2 分类原则

一个插件包只归属一个主类别，可以声明该类别内的多个可选能力。需要同时提供支付和短信等独立渠道时，交付多个插件包；不允许一个入口随意接管多个核心业务域。

| 类别 | 插件负责 | 核心系统负责 |
| --- | --- | --- |
| `provider` | 外部目录、参数转换、资源操作及查询 | 供应选择、成本与售价、订单、任务、服务归属和有效期 |
| `payment` | 渠道下单、查询、关闭、验签、退款及退款查询 | 应付和可退金额、支付归属、去重、资金流水、订单付款与对账 |
| `identity` | 发起渠道认证、查询、验签和标准结果转换 | 个人/企业及升级流程、审核、资格、会员状态和隐私管理 |
| `sms` / `mail` | 发送渠道请求和查询发送结果 | 验证码、模板、接收人、频率、通知策略和发送任务 |
| `storage` | 对象写入、读取、删除及临时地址 | 上传授权、内容检查、文件元数据、归属和访问控制 |
| `oauth` | 授权跳转、令牌交换与第三方身份查询 | state及平台支持时的PKCE、回调来源、账号绑定、会话和登录审计 |
| `product` | 经审核注册新产品定义、专属配置器和类型处理器 | 通用报价、订单、账务、履约和权限；内置云服务器仍是核心模块 |
| `feature` | 声明自己的页面、动作和已开放的扩展点 | 扩展注册、认证、授权、数据投影与业务命令校验 |

插件 ID 在所有类别中全局唯一，保留已使用的 `magic_cloud` 等稳定标识。目录、清单、入口命名空间和注册表必须一致。分类是部署组织方式，不允许变更分类来绕过权限，也不改变历史连接和订单中的插件身份。

**同系统上下游不归入 `provider` 插件。** 多上游、逐级采购、采购成本、余额冻结、链路防环和服务映射是核心业务。产品管理下可以共同展示“资源供应商”和“上游管理”，菜单归属不改变后端领域边界。外部提供者插件不处理本系统的上下游账本。

## 3. 单个插件的标准包

### 3.1 文件结构

以资源提供者为例，目标结构如下：

```text
plugins/provider/magic_cloud/
├── plugin.json                   元信息、兼容版本、能力及资源声明
├── configuration.schema.json     宿主可渲染、可校验的配置字段
├── ProviderAdapter.php           固定的类别接口入口
├── app/
│   ├── application/              插件内部调用编排，按实际复杂度设置
│   └── infrastructure/           平台客户端、签名与参数转换
├── migrations/                   可选，仅插件自有数据的受控迁移
├── resources/
│   └── admin/                    可选，审核后的前端构建产物
├── tests/                        契约及外部接口测试
├── README.md                     配置、能力、适用版本和故障说明
└── CHANGELOG.md                  升级及存量兼容说明
```

简单渠道不强制创建所有层；配置声明和固定入口必需，其他目录按需提供。运行日志、上传文件、密钥和缓存位于宿主管理的私有运行目录，不能写进插件安装目录。源码交付可以包含测试与开发说明，生产安装包裁剪测试资料和开发依赖。

目标自动加载前缀为 `plugins\\`，例如 `plugins\provider\magic_cloud\ProviderAdapter`。宿主由类别和插件 ID 推导入口，校验它确实实现指定接口；清单和 HTTP 参数不能提供任意类名、任意文件路径或可执行 PHP 配置。

### 3.2 清单负责声明，入口负责执行

`plugin.json` 至少声明以下内容：

| 字段 | 要求 |
| --- | --- |
| `manifest_version` | 清单结构版本，与业务 SDK 版本分别管理 |
| `id`、`category`、`name` | 稳定 ID、允许的类别和客户可理解的名称 |
| `version`、`publisher`、`license` | 包版本、发布主体和许可证 |
| `requires` | Core、PHP、公共 SDK 与类别 SDK 的兼容范围 |
| `capabilities` | 固定能力名称、契约版本及声明的限制 |
| `configuration_schema` | 包内配置 Schema 的安全相对路径 |
| `catalogs` | 提供者的外部目录与标准资源类型声明，其他类别可省略 |
| `permissions`、`frontend` | 可选的权限及预构建页面声明 |
| `migrations`、`data_policy` | 可选迁移版本以及停用、卸载时的数据保留策略 |

以下为清单主要字段示意；完整可运行清单还必须包含 `provider` 和 `network`，以 [魔方云清单](../../backend/plugins/provider/magic_cloud/plugin.json) 为准：

```json
{
  "manifest_version": "1.0",
  "id": "magic_cloud",
  "category": "provider",
  "name": "魔方云",
  "version": "1.0.0",
  "publisher": "howstack-team",
  "license": "Apache-2.0",
  "requires": {
    "core_min": "0.1.0",
    "core_max_exclusive": "1.0.0",
    "php_min": "8.3",
    "plugin_sdk": "1.0",
    "provider_sdk": "1.0"
  },
  "configuration_schema": "configuration.schema.json",
  "capabilities": {
    "provider.connection_test": true,
    "provider.catalog": true,
    "provider.binding_validation": true,
    "cloud_server.provision": false
  },
  "permissions": [],
  "frontend": [],
  "migrations": [],
  "data_policy": "retain"
}
```

当前协议统一为 v1，清单和配置协议字段使用 `1.0`，供应接口使用明确 DTO；不保留旧数组协议或双版本加载。魔方云当前包版本为 1.1.0，插件包版本独立于协议版本，资源生产仍未开放；清单、安装状态与能力各自校验。

“已经安装”“已经启用”“连接认证成功”和“支持开通”分别判断。可调用能力必须同时满足：接口实现、清单声明、具体连接的能力检查、配置有效、用户权限、对象归属及商业功能授权。清单声明不能自行获得权限，商业插件不能修改授权结果。

## 4. 配置管理

### 4.1 配置分层

**每个插件都要有配置入口**；不需要额外字段的插件显示“无需额外配置”和测试结果，不要求开发者编造配置项。

| 层次 | 示例 | 管理方式 |
| --- | --- | --- |
| 包定义 | 名称、版本、能力、配置字段 | 随不可变安装包发布，不保存客户值 |
| 插件级设置 | 某功能插件的工作模式或默认行为 | 宿主统一配置页保存，按插件隔离 |
| 连接级设置 | 魔方云平台地址与账号、支付商户号、短信渠道密钥 | 资源供应商连接独立保存、版本化和测试；基础服务通道每个插件直接配置并启停，不提供新增通道 |
| 产品/业务绑定 | 地域映射、节点映射、支付方式绑定、短信模板对应 | 保存在所属核心业务模块，不混入通用插件配置 |

“设置了渠道密钥”不能代表选定了所有产品、支付商户或发送模板。系统默认渠道与连接选择由核心业务配置负责，插件只收到当前调用需要的连接。

### 4.2 配置字段协议

配置字段声明 `key`、中文 `label`、类型、必填、默认值、长度/范围、枚举、单位、说明和敏感标记。初期开放 `text/password/url/integer/boolean/select` 等固定类型，不支持上传可执行脚本、自定义 JavaScript 校验器或任意 React 组件名。

魔方云的连接配置示例：

| 字段 | 显示名称 | 类型与限制 | 保存与输出 |
| --- | --- | --- | --- |
| `api_url` | 平台地址 | 必填 URL，最长 512 字符，宿主审核访问范围 | 按连接保存，可在设置页回填 |
| `username` | 登录账号 | 必填文本，最长 128 字符 | 按连接保存，仅在设置页回填，不列入供应商列表 |
| `password` | 登录密码 | 必填私密字段，最长 2048 字符 | 加密保存，更新留空保留，只返回是否已配置 |

宿主将受限配置 DSL 转换为表单与校验规则；当前供应插件仅支持连接级配置，其他类别的插件级配置在其运行契约交付时增加。插件开发者无需实现独立的配置保存接口。

- 宿主统一生成 Arco 表单，开关使用 `round`；密钥使用私密输入，不进入列表或公开 DTO。
- 必填、类型、范围、未知字段和有限的字段依赖由宿主 Schema 校验；插件的固定配置校验方法只补充平台特定规则。
- 保存遵循“白名单验证 → 插件纯配置校验 → 规范化 → 加密保存 → 版本递增 → 使测试状态失效”。测试另行触发，保存配置不隐式发送、扣款或生产。
- 私密字段留空表示保留旧值；清除凭据必须是明确动作。API 返回非敏感值与 `configured_secrets` 标记，不返回可逆密文。
- 连接地址变更后重新验证网络范围、认证和能力。供应映射的兼容性按供应模块规则处理，历史发布绑定和订单快照不覆盖。
- 密钥仅在受控调用中解密，日志统一脱敏。异步任务保存连接引用和必要版本信息，避免复制明文秘密进入消息或快照。
- 凭据轮换更新当前安全凭据，历史任务仍保留原供应身份；需要继续完成任务的旧凭据如何保留、撤销和清理由凭据服务明确管理。

配置 Schema 自身需要受限解析：限制大小、深度、字段数，不解析远程 `$ref`，不执行 Schema 中的字符串。字段规范和语义变化必须提供配置迁移；必填项新增或旧字段删除不能导致存量连接被静默改写。

## 5. 固定接口与自定义逻辑

### 5.1 统一调用规则

开发者可以在插件内部自定义客户端、签名算法、外部字段转换和接口调用逻辑。**宿主只调用已发布接口中的固定方法**，不提供 `execute($method, $payload)`、任意函数名回调、反射调用或任意服务定位器。

采用“必要接口 + 可选能力接口”，不设计要求所有插件实现几十个方法的万能基类：

| 层次 | 固定约定 |
| --- | --- |
| 公共配置接口 | `validateConfiguration()`，只校验和规范化，不执行外部副作用 |
| 类别必要接口 | 提供该类别最小有效功能，如供应测试与目录、短信发送、对象存储 |
| 可选能力接口 | 查询、回调、退款、生产、重装等独立接口；实现并声明后才能启用 |
| 宿主注入 | 类别限定的 HTTP 客户端、配置上下文、日志及必要的私有存储能力 |

构造函数只接收固定的、范围受限的 SDK 依赖，不执行网络访问、数据库迁移或业务操作。可变的连接配置、当前用户和任务上下文按每次调用显式传入，不能留在 Webman 常驻单例或静态属性中。

### 5.2 资源提供者

当前供应 v1 提供四个固定 DTO 方法：

| 当前方法 | 输入 / 输出与边界 |
| --- | --- |
| `validateConfiguration()` | `Configuration` → `Configuration`；平台特定配置校验及规范化，无 HTTP |
| `testConnection()` | `ConnectionContext` → `ConnectionTestResult`；只读认证测试 |
| `listCatalog()` | `ConnectionContext`、`CatalogQuery` → `CatalogPage`；声明目录及有限分页，无资源创建 |
| `validateBinding()` | `ProviderBinding` → `void`；使用宿主传入资源、映射和目录校验，无数据库、HTTP 或生产 |

宿主内部调用端口经 Infrastructure 转换为这些 DTO，不作为第三方插件入口。生产阶段再开放以下可选接口，未实现的能力不显示操作入口：

| 能力接口 | 固定方法 | 输入/输出含义 |
| --- | --- | --- |
| 供应目录 | `testConnection()`、`listCatalog()`、`validateBinding()` | 连接上下文、分页及绑定 DTO，返回测试结果、标准目录和字段/组合错误 |
| 云服务器开通 | `create()`、`queryOperation()` | 完整 `ProvisioningRequest` 和操作编号，返回 `OperationResult` |
| 资源查询 | `getResource()` | 本次调用的供应绑定与外部 ID，返回标准资源观测结果 |
| 电源控制 | `start()`、`stop()`、`restart()` | 受授权的资源操作请求 |
| 重装 | `reinstall()` | 已校验镜像、磁盘与短期凭证引用 |
| 续期 | `renew()` | 续费请求、账期与操作幂等键 |
| 释放 | `release()` | 终止操作及释放语义，结果需可核查 |

上表按能力拆分接口，不能要求魔方云、域名或 SSL 提供者实现不适用方法。未支持的能力返回固定“不支持”错误，不把空结果或未执行当成成功。

核心传入地域、可用区、线路、规格组、规格、镜像、完整磁盘数组、网络、防护、周期及所需凭证引用，同时提供封存的外部映射。插件理解并转换这些结构，不读取核心配置表。供应目录同步不能改商户价格、销售方案或历史订单。

`OperationResult` 明确区分 `succeeded/accepted/failed/unknown`，包含安全错误码、操作引用和可查询的外部标识。资源观测状态与销售服务状态分开；插件不能因外部显示“运行中”自行认定订单完成或延长服务有效期。

### 5.3 支付、实名、通知和存储

以下均为待建设的类别 SDK，发布前需补齐每个方法的参数、DTO、失败和幂等语义：

| 类别 | 固定方法 | 必须守住的边界 |
| --- | --- | --- |
| 支付 | `createPayment()`、`queryPayment()`、`closePayment()`；可选 `refund()`、`queryRefund()`、`verifyNotification()` | 只能执行核心指定金额与币种；验签输出交易证据，不能修改订单或余额 |
| 实名 | `startAuthentication()`、`queryAuthentication()`；可选 `verifyNotification()` | 返回标准核验结果及证据引用；不直接修改会员的个人/企业认证状态 |
| 短信 | `send()`；可选 `queryDelivery()`、`verifyNotification()` | 只发送指定接收人、模板和变量；不能自行生成验证码、批量选会员或决定业务频率 |
| 邮件 | `send()`；可选 `queryDelivery()`、`verifyNotification()` | 只提交宿主生成的邮件与附件引用；不遍历核心文件或更改通知策略 |
| 存储 | `putObject()`、`getObject()`、`deleteObject()`；可选 `createTemporaryUrl()` | 宿主签发对象范围和内容流，插件不能自行选择任意本地路径或扩大私有文件权限 |

回调使用宿主固定入口，例如 `/api/public/v1/plugins/<plugin_id>/callbacks/payment`。具体连接由宿主签发的不透明标识或可靠的渠道字段匹配，不能相信客户端提交的会员、连接 ID 或金额。支付/实名等验签需要原始请求体和必要 Header 时，仅向对应插件传递有大小限制的回调 DTO；验签后还要由核心核对商户、业务归属、金额、币种及重复/乱序事件。

支付渠道要求特定响应格式时，宿主按审核过的固定应答协议生成响应；普通业务 API 继续采用本系统 `ApiResponse`。插件不自行注册可以绕过认证的公开控制器。

### 5.4 功能插件与产品扩展

功能插件的后台能力通过静态清单声明页面、Slot 和固定业务动作。后端只对清单中审核通过的动作映射到明确类型的处理器，不接受用户提供 PHP 方法名或无约束参数包。动作输入输出均有独立 Schema 和权限。

- 读数据：调用 SDK 开放的白名单查询，返回受控投影，不返回 ORM 模型、密码、密文和完整核心对象。
- 写核心业务：提交已开放的 Application 命令，核心再次校验权限、归属、状态和业务不变量。
- 插件自有数据：通过限定插件表范围的存储接口操作；核心 ORM 与 Repository 实现不作为 SDK。
- 事件扩展：订阅公开、脱敏、版本化事件；只读通知不允许修改原事件或覆盖核心处理器。可靠后续操作进入宿主持久化任务，不能只靠进程内事件。
- 产品扩展：通过 `ProductTypeDefinition` 与 `ProductTypeHandler` 提供明确类型、专属配置校验、计价和生产请求；安装时审核稳定 `definition_key`，不恢复后台任意新增产品类型的 CRUD。

首期不开放通用 PHP 启动脚本、全局 `before/after` 钩子、任意定时进程或“调用任何核心服务”的功能。新增扩展点先定义业务目的、权限、输入输出及兼容版本，再加入 SDK。

## 6. 权限与依赖边界

### 6.1 宿主能力按需授予

| 能力 | 插件可以获得 | 不向插件开放 |
| --- | --- | --- |
| HTTP | 供应使用受限门面；邮件可使用插件本地依赖客户端访问本次配置的平台，由插件校验超时、TLS 和重定向并经审核 | 任意 URL、自动跳转到未授权地址、关闭 TLS 校验 |
| 配置 | 当前插件/连接必要字段，按调用授权解密 | 其他插件配置、全量 `.env`、核心凭据 |
| 日志 | 带插件、连接、操作编号的脱敏日志接口 | 密码、Cookie、Authorization、完整原始财务/实名报文 |
| 缓存 | 按插件及连接隔离、有期限的非敏感缓存 | 任意 Redis 命令、核心 Session 与其他插件缓存 |
| 文件 | 宿主签发的对象引用、限额临时文件和隔离目录 | 任意路径、配置文件、核心源码和任意公开资源写入 |
| 数据 | 固定 DTO、白名单只读查询、自有数据范围 | 核心 `Db/Model/Repository`、跨模块直接写入 |
| 任务 | 已声明处理器、核心签发的任务与幂等键 | 任意进程、Shell、修改 Worker、直接调度扣款或生产 |

提供者可能部署在内网，例如 Proxmox VE。网络策略应允许管理员明确配置的内网主机和端口，同时防止地址、DNS 或重定向越界；不能为了阻止 SSRF 一刀切禁用所有内网，也不能默认允许所有私网地址。

清单中的能力申请经安装审核和运行时配置批准后才生效；管理员 RBAC、商业版功能授权和插件能力分别判断。安装插件不自动授予用户权限，前端隐藏入口不代替服务端校验。

### 6.2 边界的实际强度

这些限制由 API 设计、受限注入、清单校验、静态检查、契约测试和代码审核落实，能够减少误用并稳定升级接口。

**原生 PHP 插件与宿主同进程执行，依然属于受信代码。** 它可能直接调用 PHP/框架能力，不能声称“没有注入 Db 就无法访问数据库”。签名证明包的来源及完整性，不证明代码无恶意；静态扫描不能保证阻断所有逃逸。

若要接收未经信任的代码，后续需独立进程或容器、独立系统用户、专用凭据、文件与网络限制及版本化 RPC，且不共享核心数据库账号。接口设计提前保留可序列化 DTO，使未来隔离不需要改核心业务协议。

## 7. 宿主加载、状态与可靠执行

### 7.1 加载流程

系统只扫描固定类别根目录中的 JSON 清单。校验路径、清单版本、全局唯一 ID、包完整性、兼容性、接口和已批准能力后，建立不可变注册快照。

1. 安装期间完成审核和必要的受控迁移，记录包、配置及 Schema 版本。
2. 启动时读取启用记录与固定目录，不执行插件提供的 `config/app.php`、全局启动脚本或自动 Composer 脚本。
3. 将符合类别接口的入口交给相应核心模块；公共插件管理模块不反向依赖每个业务模块的内部实现。
4. 插件管理只描述可用能力，供应、支付等应用服务按场景授权后调用对应类别网关。
5. 动态菜单、页面和动作由宿主注册，仅采用清单白名单，处理路径、权限码和名称冲突。

插件加载错误应定位并隔离对应插件，显示安全错误和管理员诊断信息；核心登录、查询和其他有效插件继续可用。被引用插件失效时，相关新操作关闭，历史记录仍可查看。不能回退到另一插件执行同一有副作用的操作。

### 7.2 生命周期

| 状态 | 允许行为 |
| --- | --- |
| 已安装未启用 | 查看配置声明；当前供应实现须先启用插件再管理连接，不接受业务调用 |
| 已启用 | 仅执行配置有效且已确认支持的能力 |
| 停止接单 | 禁止新操作；存量查询、回调和任务收尾继续 |
| 升级/排空 | 锁定安装生命周期，按任务和兼容策略受控处理 |
| 已停用/异常 | 关闭新操作；保留数据及未决事件，必要收尾通过专用路径或恢复插件后执行，明确相关操作不可用 |
| 已卸载 | 仅在无存量业务引用、资金与任务未决状态时进入；保留的数据仍按归档策略管理 |

停用与卸载区分；不能停用支付插件后丢弃尚未确认的回调。涉及运行服务的插件需要持续查询、续费或售后时，先迁移供应关系并确认业务收敛。保存设置不触发升级，审核通过不等于测试通过。

新包先进入私有暂存区。校验压缩大小、路径穿越、符号链接、重复文件、签名/摘要和兼容性后发布版本；数据库和启用状态通过受控事务更新。Worker 使用同一注册版本，外部写任务在切换时暂停或排空。跨文件系统、数据库和进程的切换没有单一原子事务，须记录部署阶段、失败恢复及前向修复步骤。

自动加载器、配置、路由或启动绑定改变时完整重启 Webman。代码回退必须与数据结构兼容，不能为了回退插件而盲目回滚已有资金或服务数据。

### 7.3 外部副作用由核心任务承载

核心负责操作记录、幂等键、执行租约、重试策略、回调去重、乱序处理和主动对账。调用链为：

```text
后台/会员请求 → 核心认证与授权 → 类型/业务校验
            → 事务提交任务与必要账务 → 受控 Worker 调用固定插件方法
            → 标准执行结果 → 核心核对证据并推进业务状态
```

插件自行实现外部签名、认证和参数转换，不能自动切换连接、生成新的付款/开通编号或无限重试。若外部 API 支持幂等则使用核心签发的键；不支持时要定义查询及查重规则，不能宣称实现了远端恰好执行一次。

超时或断线导致 `unknown` 时，核心先查询是否创建资源、扣款或退款。查清前禁止重新生产、换供应商、释放相关资金冻结或宣布失败已收敛。纯查询可以有有界重试；有副作用调用由任务策略决定。

## 8. 插件数据、前端与开发体验

### 8.1 数据归属

插件安装、配置、启用和生命周期记录属于插件管理模块；供应连接、映射及绑定属于供应模块；商户支付配置和交易记录属于支付/财务模块。

只有确需持久化的插件专属数据才允许创建自有表，逻辑表名使用 `plugin_<plugin_id>_*`，实际表名前缀由连接配置应用。每张表、字段设置中文注释。插件迁移保存在本包内，使用独立迁移记录，由宿主维护命令受控执行；不得插入核心迁移目录、改核心结构或在普通请求中建表。

优先声明式变更；确需 PHP 数据迁移时视为已审核受信代码，规定输入、范围、幂等及失败恢复。通过命名检查减少误改，不把表名前缀当作数据库权限隔离。卸载不默认删数据，连接凭据与个人资料仍须遵循明确的数据保留和销毁策略。

### 8.2 前端扩展

- 普通插件配置用主应用的 Arco 表单，无需插件另写页面。
- 需要独立界面的 `feature/product` 插件交付预构建资源，声明后台、会员或门户扩展点及对应版本；客户服务器不安装前端依赖或编译。
- 使用公开 SDK 的 DTO、请求、路由、权限、组件与主题能力，不引用主应用私有 Context、Store、组件源码或内部 API。
- SDK 按各应用 React/Arco 主版本声明兼容；不向页面重复注入不兼容的 React 实例或全局 CSS。
- 页面挂载、卸载、缓存失效、错误边界、资源加载失败及禁用回退由宿主控制。不采用 iframe；同域 JavaScript 同样须审核。
- 普通 API 使用 `/api/<入口>/v1/plugins/<plugin_id>`；页面路径由宿主与清单匹配，不恢复 `/app` 前缀、不覆盖核心页面或路由。
- 新页面注册访问权限，操作单独授权；详情及批量操作仍检查对象归属。

### 8.3 让开发者只处理必要逻辑

SDK 发布时交付以下资料：

1. 按类别的脚手架：正确目录、清单、配置字段和最小固定入口。
2. 接口参考：方法签名、DTO、单位、状态、异常、超时和副作用说明。
3. 魔方云只读插件示例与脱敏的接口 fixtures，明确供应平台兼容版本。
4. 契约测试工具：测试清单/配置、目录映射、多个连接、能力缺失、异常和结果未知。
5. 校验命令：检查禁止依赖、公开路由越界、包内容、配置与前端资源兼容。
6. 升级指南：SDK 弃用期、字段变更、配置迁移、历史绑定与存量服务兼容策略。

开发者不需要重做后台登录、权限、列表配置表单、资金流水、队列重试或插件启停页面。确需新扩展点时提出契约，不能以直接访问核心内部实现作为长期接入方式。

## 9. 从当前实现迁移

### 阶段一：目录调整与供应回归

1. 固定当前魔方云/测试插件的注册、连接配置、认证、目录和映射回归基线。
2. 新增受控 `backend/plugins/provider/`，移动魔方云及其内部类，更新命名空间与自动加载。
3. 更新 `LocalProviderAdapterRegistry`、`config/dependence.php`、文件监控、测试 fixtures、路径与打包清单。全部供应插件遵循统一 v1 协议，注册器只接受公共 DTO 接口及受限 HTTP 客户端，HTTP 响应及权限码不变。
4. 保持 `magic_cloud`、`adapter_id`、连接和映射身份不变，核对配置密文可解、历史绑定及快照可读；目录移动不修改客户业务 ID。
5. 检查框架应用插件引用及安装部署路径，确认无剩余文件和用途后移除 `backend/plugin/` 与当前项目的旧 `plugin\\` 自动加载映射；保留 `config/plugin/`、依赖和框架代码。
6. 完整重启并验证不同 Worker 一致性，完成认证及目录查询回归。

### 阶段二：统一清单、配置与 SDK

1. 发布统一 v1 清单、配置 Schema 和公共接口；提供类别入口及 DTO，所有插件执行相同的依赖与网络边界校验。
2. 将旧 `provider.json` 和 `config/app.php` 的声明与启用状态迁移到新清单和宿主记录，禁止长期同时扫描新旧目录。
3. 用新 Schema 渲染配置，维持旧 API 私密字段回填规则；未知配置禁止悄悄丢弃，提供显式迁移结果。
4. 历史绑定仍保存原 SDK/包版本及清单摘要；旧摘要不重算冒充原版本。明确已发布配置的兼容区间，需要重测时阻止新发布。
5. 建设启停、配置测试、加载失败隔离和安装生命周期。只有实际引用自有表的插件才执行必要迁移。

### 阶段三：生产与其他插件类别

在持久化任务、Outbox、凭证管理及对账边界完善后，增加供应生产及支付退款契约；再逐项增加短信、邮件、实名、存储和功能扩展。先完成真实测试环境验证，再标记具体能力可用，不因统一插件目录已经建立就宣称所有渠道可用。

进程隔离按信任模型另行建设，不阻塞受信插件的规范化开发，也不向客户承诺同进程插件已有硬隔离。

## 邮件通道 v1 已实现边界

短信与邮件根目录入口现在可独立实现模板提交、审核查询接口，宿主根据实际接口识别 `template_review.submit/query`，不重复增加清单能力字段。提交受理与审核结论分开，使用原通道和配置修订，不自动重发或启用消息；具体契约和交付边界见 [模板审核接入](../plugins/message-template-review.md)。

邮件采用“清单 + 配置字段 + 固定入口”的最小接入形式。`MailAdapter` 只实现 `validateConfiguration(Configuration)` 和 `send(MailMessage, Configuration)`；每次传入当前配置与邮件内容，插件直接实现外部平台发送。SMTP 插件在 `plugins/mail/smtp` 内使用 PHPMailer，其他邮件平台可使用自己声明、锁定并构建的 HTTP 客户端，不要求核心添加平台分支。SMTP 的专有配置校验和协议状态跟踪留在本插件内部，不放入公共 SDK。

宿主统一负责表单、凭据加密、权限、启停与安装生命周期、发送记录及幂等，不要求开发者重复实现这些能力。第三方客户端属于受信插件依赖，网络声明与静态检查不是沙箱；访问配置范围、TLS、超时和结果分类须由插件实现并经审核。供应插件仍使用其受限 HTTP 门面。免费内置包首次登记走核心前向迁移，不依赖官网授权。详见 [通道管理](../development/channel-management.md) 的接入步骤、结果状态和幂等规则。

## 插件本地第三方依赖

第三方 SDK 由各插件自己的 `composer.json`、`composer.lock` 管理，生产 vendor 预构建后随插件交付；不修改主项目 Composer，不在客户安装时执行 Composer。宿主在已审核并启用的包上校验锁定版本、加载路径、核心命名空间与 SDK 版本冲突后加载本地依赖，源码及 vendor 均参与包摘要。独立目录不提供 PHP 命名空间隔离，同名不同版本拒绝混用；依赖变更须审核升级并完整重启。详细构建、交付与冲突处理见 [第三方邮件通道插件开发文档](../plugins/mail-channel-development.md#插件自己的-composer-依赖)。

## 公共 HTTP 快捷能力

插件可按需引入第三方 Composer SDK，不采用包名白名单；完整性、版本冲突及宿主能力边界仍执行。系统提供公共 HttpClient 的 GET/POST/PUT/DELETE、POST 表单及通用请求，默认校验证书、有限超时、不重试、不跳转、响应体最多 2 MiB。常规 HTTP 插件无需额外声明 Guzzle；第三方 SDK 接入仍可选择自己的客户端并承担相应协议约束。供应端的 ScopedHttpClientInterface 也提供四种快捷方法，保持既有连接及端点校验。详见 [公共 HTTP 请求指南](../plugins/http-client.md)。

## 支付与身份验证 v1 已实现边界

支付宝订单码插件实现 `create/query/close/verifyNotification`，身份验证插件实现 `initialize/query`，采用公共 DTO、配置加密和启用包摘要校验。两者无插件自有表、路由、前端或任意业务钩子。退款、企业实名认证、完整在线收银和会员自动认证流程尚未交付；前文扩展契约为后续规划。

按项目决定，两个官方支付宝插件共用主 Composer 中的 `alipaysdk/easysdk`，各自目录不含 Composer/vendor；第三方插件仍可独立声明 SDK，不能修改宿主依赖。每次调用创建独立 SDK Kernel，加验签由 SDK 完成，传输使用宿主公共 HTTP 能力；不缓存商户配置，不使用静态 Factory。详见 [支付宝通道接入与插件开发](../plugins/alipay-channels.md)。

### 人机验证与官方通道依赖

`captcha` 使用固定 v1 的 `initialize/fingerprint/verify` 契约，不能写入业务认证状态。场景、会话与可信 IP 由宿主指定，挑战与证明一次性消费，平台异常不得放行。阿里云、腾讯云与微信支付 SDK 由各自插件目录的 Composer 及锁文件管理，宿主只加载经审核的生产 vendor；支付宝继续按现有约定使用主 Composer。七牛直接实现 REST，不使用 SDK。见 [人机验证开发指南](../plugins/captcha-channels.md)。
