# 财务管理：订单与订单项

## 当前实现

运营后台在“财务管理 / 订单管理”提供分页、关键字及状态筛选，并在详情抽屉展示订单项。`GET /api/admin/v1/orders` 和 `GET /api/admin/v1/orders/{id}` 均要求 `admin.page.order-list.view`；无此权限时菜单与接口都不可用。接口契约见 `contracts/openapi/admin-orders.v1.yaml`。

`orders` 保存订单号、会员标识及名称快照、订单与支付状态、币种和最小货币单位金额；`order_items` 以 `order_id + line_no` 归属订单，保存产品类型版本、销售版本、名称、数量、单价和小计。订单详情不返回可能含业务配置的 `configuration_snapshot`。MySQL 使用外键保护会员、订单和订单项的关系；会员有订单时只能禁用，不能删除。

后台仍只提供订单查询，没有订单创建、状态修改或退款办理入口；会员余额付款沿用原有接口，由订单模块的 `PayOrderByWalletService` 编排。当前没有订单创建及单位分摊写入流程，不生成演示订单。数据库为空时列表展示空状态。新增的迁移 `20260927000100` 不可逆；已有安装实例升级前按升级规范备份，失败时通过前向修复迁移处理，不能回滚删除交易数据。

## 确定设计

后续订单必须从经过服务端校验的有效报价创建，订单项是当时的产品类型、销售版本、配置和金额快照。金额计算只使用整数最小货币单位；支付、退款、交付状态分别管理。订单号和支付回调需要幂等约束，订单与账务、履约之间采用持久化任务和 Outbox。配置快照不得包含密码、私钥或支付凭证。

## 后续扩展

报价、下单、支付、退款、服务和账务闭环完成后，再增加订单操作权限及对应入口。届时需要验证重复回调不会重复扣款或生产、历史订单不受销售调价影响、退款和上游采购异常能够恢复。

## 订单单位与服务首次来源

迁移 `20261001000200` 在 `service_instances` 新增可空且唯一的 `origin_order_unit_id`，固定首次交付来源；`order_item_units.service_id` 改为普通索引，保留已有 MySQL 外键，允许续费或升级单位指向同一服务。服务列表通过首次来源查询订单，不从所有历史交易反查。历史无来源服务保持 null，无效关联必须人工核查后重试。退款和发票继续归属原交易单位。实施细节见 [ORM 重构说明](../architecture/current-system-refactor.md)。
