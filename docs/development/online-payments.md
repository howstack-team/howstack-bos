# 在线充值与支付确认

## 当前交付范围

PC和独立移动端均提供 `/console/finance/recharge`：读取可用通道、输入充值金额、创建付款意图、收银弹窗、本地生成/保存二维码、只读状态刷新、主动查单、取消付款及本人充值记录。资金账户和未付款订单可进入充值；从订单进入时，到账后返回原订单，仍须明确确认余额付款，不自动扣款。

本轮实现“在线收款 → 充值到账 → 余额支付订单”。复用 `recharges`、`payment_transactions`、资金来源批次、不可变流水与 `WalletLedgerService`。不把付款二维码、客户端支付成功消息或本地超时当作到账证据。后台现有充值、支付及流水查询会展示真实入账记录。核心资金表的在线渠道使用稳定的connection-ID引用，具体插件与原商户配置在支付快照中保存，不把插件命名长度限制固化到财务字段。原渠道退款、自动打款、直接在线支付商品订单及H5/JSAPI支付不在本次范围。未消费充值的人工退还见[财务流程](finance-foundation.md)，余额付款后逐实例开通见[云服务器交付](cloud-provisioning.md)。

## 配置与部署

1. 系统基础设置的官网地址填写真实可访问的HTTPS平台根地址，不带页面路径、查询参数或片段；不得由会员请求传入通知域名。服务端据此生成 `/payment-notify/<随机标识>`。
2. 在后台安装/启用支付插件并配置支付通道。当前内置支付宝订单码 `alipay_order_code`、微信Native `wechat_native`。同类别的受信支付插件通过固定SDK契约接入，核心按类别和接口加载，不按官方插件ID限制通道目录；通知接口仍须遵循宿主当前支持的表单success或微信v3 JSON/204协议。填写真实商户标识、应用标识和对应密钥，保存并启用。
3. 将公网HTTPS回调转发到Webman，保留微信原始正文和四个 `Wechatpay-*` 签名头，允许无登录Cookie的支付平台POST。回调不要求Origin，必须通过平台签名验证。
4. 部署后启动 `payment-reconciliation` Worker。它每30秒领取最多20笔到期任务，按租约执行查单；外部请求不在数据库事务内。
5. 使用商户沙箱或真实商户进行创建、付款、回调、查单及关单联调后再开放收款。

未配置HTTPS官网地址或没有有效启用通道时，接口返回 `enabled=false`，两端不提供可提交的充值表单，不生成演示支付方式或虚构二维码。

移动端复用现有扫码支付协议，支持二维码保存。微信Native是扫码协议，不等同于同设备H5跳转或公众号JSAPI；这些能力须使用相应支付插件和商户权限，不能通过前端自行改写协议。二维码使用本地MIT许可证的 `qrcode` 1.5.4生成，不请求外部图片服务。

## API与通知协议

内部API均在 `/api/console/v1/recharges`，使用会员HttpOnly Cookie和统一ApiResponse；写请求必须同源Origin，归属从会话确定。

| 接口 | 用途 |
| --- | --- |
| `GET /options` | 当前通道、人民币金额范围及是否可充值 |
| `GET /` | 本人在线充值分页，默认20条 |
| `POST /` | 传入channel_id、整数分amount_minor及request_key，创建或返回原意图 |
| `GET /{id}` | 只读本地状态，不调用上游 |
| `POST /{id}/query` | 使用原快照主动查单，确认收款后原子入账 |
| `POST /{id}/close` | 先查单，再关闭未付款交易；未知时继续核查 |

契约唯一源为 `contracts/openapi/console-recharges.v1.yaml`，文档入口 `/api-docs`。

第三方协议回调位于 `/api`之外，避免统一业务JSON封装破坏平台ACK：

- 支付宝接收原始表单值，拒绝重复键和数组，验证RSA2签名、app_id、seller_id、商户付款单号及人民币金额。提交账务后返回HTTP200、纯文本 `success`；失败返回非成功HTTP状态和 `failure`，让平台按协议重试。
- 微信接收原始JSON与签名头，校验RSA签名、时间窗、受信公钥标识，再用原API-v3密钥进行AES-GCM解密，核对appid、mchid、付款单号、金额和币种。提交后返回HTTP204；失败返回HTTP500及平台格式的FAIL JSON。

随机回调标识只定位原支付，不授予支付确认权限。参考[支付宝官方异步通知说明](https://help.alipay.com/support/help_detail.htm?help_id=491081)和[微信官方Native支付指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791891)。

## 持久化、状态与并发

新增 `online_payment_attempts` 保存通道ID/修订、插件审核摘要、原商户配置加密快照、会员意图键/摘要、回调路由、二维码、到期时间、查单调度及租约。配置、随机路由和租约不通过会员API返回。创建操作保存经统一解析的IP和位置快照；通知记录只保存原文SHA256及来源IP/位置，不保存原始支付报文、签名、付款人或密钥。

金额为人民币整数分，范围1至100000000分。付款单号最长31位，兼容微信商户单号上限；同会员同request_key同金额/通道返回原交易，改变请求返回409。客户端在当前标签页保留两小时金额/通道/随机键，刷新或网络失败重试沿用同意图，不存密码、Cookie令牌或商户参数。每会员最多10笔未确认充值，并对写操作限流。

核心支付状态：

| 状态 | 含义 |
| --- | --- |
| creating | 已持久化，创建请求处理中或尚待结果 |
| pending | 上游已接受，尚未确认付款 |
| unknown | 上游结果不确定，不能重新创建原付款 |
| paid | 已通过验签/查单确认，并完成余额到账 |
| closed | 上游明确确认已关闭 |
| failed | 创建请求明确失败，不表示未知结果 |

原交易按快照收尾；通道编辑、停用或归档不替换原商户配置。插件进入draining后仍允许原流水验签、查单与关单；未确认交易以及七日通知窗口内的快照参与插件引用保护，阻止停用、换包和卸载。收尾加载器只接受原审核摘要匹配的受信插件，不是任意代码执行入口。

锁顺序为充值、支付交易、执行快照、资金账户及来源批次。已验签paid后，支付状态、充值状态、资金来源、不可变流水、余额和收款消息在同一业务事务提交。核实交易及通知去重使用锁定读取，避免MySQL快照读误判刚刚完成的并发入账。重复回调和主动查单最多入账一次，已付款状态不被旧的pending/closed结果覆盖。来自原商户的有效迟到付款仍按实际收款入账，不能因本地展示已过期丢弃真实收款。

网络未知或程序中断不自动重复发起创建请求。执行租约120秒，并以随机租约令牌拒绝旧执行结果覆盖新租约；已确认真实付款仍须接收处理。查询至少间隔5秒，自动查单退避最多30分钟。15分钟仅是付款展示期限，确认未支付后才请求关单。自动核查七日仍未知时转人工提醒，禁止人工把未核实金额改成paid；原流水仍可核查，未知交易仍参与插件引用保护。

受控CLI：`php webman payment:reconcile <后台支付记录ID>`。它核查原流水并按真实结果结算，未付且到期时按既有规则请求关单；不创建新的上游付款，也不提供强制到账开关。

## 迁移与验收

前向迁移 `20261015000300_create_online_payments.php` 新增执行快照，扩展通知IP/摘要及交易号长度；不修改已执行迁移。执行前备份数据库，再通过 `php webman system:migrate --force` 升级，完整重启Worker。

实际验证应区分以下证据：

- `HOWSTACK_MYSQL_TEST=1 vendor/bin/phpunit tests/integration/OnlineRechargeWorkflowTest.php tests/integration/OnlinePaymentMigrationTest.php`：独立MySQL迁移、前缀、升级保留历史数据、中文注释、幂等、重复通知、查单恢复、关单竞争与三个独立进程的到账竞争。
- `AlipayAdaptersTest`、`WechatNativeTest`：临时RSA密钥、真实SDK签名/AES与受控HTTP回复，验证商户身份、金额、响应和通知协议。不是平台真实联调。
- `HOWSTACK_RECHARGE_HTTP_ACCEPTANCE=1 php tests/acceptance/online-recharge-http.php`：仅本机开发数据库，临时商户密钥的真实HTTP通知验签、篡改拒绝、重复ACK、原子入账及清理；上游支付调用0次。
- `HOWSTACK_PLAYWRIGHT_MODULE=<Playwright模块> node frontend/console/tests/recharge-browser.mjs`：模拟API下的PC/Mobile字段校验、反馈、网络重试保留幂等键、收银弹窗、刷新、未知状态、余额刷新、入口关闭及390/320px布局。
- 正式收款前另做真实沙箱/商户创建、手机扫码付款、重复通知、回调不可达后查单恢复、关单竞争、凭据/通道变更收尾及支付账单核对。

## R05 支付验收预检与账务核对

只读命令 `php webman payment:check` 检查平台HTTPS根地址、内网/保留测试地址及当前可用支付通道。追加后台支付记录ID可核对该笔在线充值：

```bash
php webman payment:check
php webman payment:check 123 --json
```

可选ID为**后台支付记录内部ID**，不是会员充值ID。工具不调用支付平台、不创建付款、不查单/关单、不修改支付/充值状态或余额，也不会创建原本不存在的钱包。需要向平台查证原笔支付时，仍明确执行 `php webman payment:reconcile <支付记录ID>`；这与本地只读核对是不同操作。

核对覆盖支付与充值的归属、金额、CNY币种和原通道、唯一入账流水、唯一资金批次、原充值剩余+净消费+冻结/已退还金额守恒，以及当前账户可用余额、来源批次、全部流水与冻结申请是否一致。已消费、已退回余额、充值来源冻结/驳回/打款后的正确账务不能被误判为“没到账”。异常只报告，不自动改账或强制成功。

报告不包含商户私钥、配置密文、随机通知路由、签名正文、完整渠道交易号或会员联系方式。若保存JSON证据，应在私有目录使用限制权限的文件，并补充执行人、候选版本/包摘要及商户侧证据编号；不要上传到公开素材库。

退出码：0仅表示配置具备外部测试条件且所选交易本地一致；1表示配置未就绪或本地账务不一致；2表示命令参数无效。**0不表示真实商户验收通过或1.0放行**。报告始终保留 `external_verification=pending`、公网回调连通与商户账单 `not_tested`，这些只能由真实测试记录关闭。读取使用数据库默认事务隔离；核对期间若存在持续资金活动，应待原业务提交后复核并与平台账单核对。

### 官方微信插件的共享SDK约束

R05回归发现，宿主安装 `guzzlehttp/uri-template` 2.0.1时，官方微信SDK 1.5.0要求1.x，宿主加载器会正确拒绝加载。现将宿主显式锁定为与插件相同的1.0.11；Illuminate允许该版本。只调整此依赖，不放宽加载器版本/来源校验，不修改vendor或原支付插件包、不改变历史商户快照。依赖更新后完整restart；发布前应同时核对宿主与插件锁文件，不能各自独立升级共享包。Composer对精确版本的提示是此兼容约束的预期结果。

本地验证及真实商户执行步骤见 [R05验收记录](../releases/community-1.0-r05-payment-acceptance.md)。PC/移动扫码协议和二维码下载的模拟浏览器验证，不代表手机支付应用或同设备支付已验证。
