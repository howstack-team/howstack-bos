# 财务管理实施状态

## 当前实现

后台“财务管理”已有订单管理和六类财务记录查询入口：充值记录、支付记录、资金流水、退款记录、发票记录、提现记录。六类记录分别拥有真实页面访问权限、服务端权限校验、分页查询及详情接口；暂无资金操作按钮。查询契约见 `contracts/openapi/admin-finance.v1.yaml`。

前向迁移 `20260927000200` 创建实例级金额、资金账户、充值来源批次、支付交易、资金流水、退款尝试、发票金额归属、提现申请及财务 Outbox 等基础表。已执行的订单迁移不修改。`OrderUnitAllocator` 使用整数最大余数法，将订单实付金额确定性地分摊至每台资源。

`WalletLedgerService` 负责已确认充值入账、资金支付核对和来源扣减；订单付款由订单模块 `PayOrderByWalletService` 编排。资金仓储不访问订单表。前者要求存在金额、币种、渠道和会员均匹配的成功支付交易；后者要求订单实例金额已经完整分摊。两个用例通过共享 `TransactionManagerInterface` 使用默认连接事务；订单、账户、来源批次按固定顺序锁定。余额扣款与支付记录、订单付款确认及显式 `order.paid` Outbox 一起提交或回滚。充值入账尚未开放公开调用；余额支付已通过会员接口开放，但由于当前缺少订单创建和实例分摊写入流程，现有订单不能直接用余额支付。

会员控制台现提供手机号密码登录、本人余额展示和退出登录。后端接口包括 `/api/console/v1/auth/login`、`/auth/me`、`/auth/logout`、`/wallet` 和 `/orders/{id}/pay-wallet`，均使用同一 `/api/console/v1` 前缀，契约见 `contracts/openapi/console-finance.v1.yaml`。余额支付以登录会员身份检查订单归属；会员会话使用独立于后台管理员的 Cookie 和令牌受众。会员控制台构建产物由 Webman 的受控静态资源路由提供。

前向迁移 `20260927000300` 删除会员用户名，并把订单展示字段改为会员手机号快照。升级前必须让既有会员都有手机号；迁移在发现缺失手机号时会停止，避免账号无法登录。当前仅支持手机号加密码，后台录入的手机号尚未经过短信验证；手机号验证码登录、本人绑定及换绑流程需要短信插件和验证状态后另行实现。

## 尚未开放的交易能力

- 会员端购买、有效报价生成、销售版本校验、订单创建及服务实例尚未完成；因此当前无法完成真实购买和自动续费。
- 微信与支付宝插件、商户配置、支付回调验签、渠道查询和对账尚未完成；后台充值和支付记录当前只提供查询，不提供在线收款。
- 退款资格及金额计算、资源释放确认、渠道退款、审核状态机、发票红冲、例外提现复核与打款均尚未接通；后台仅显示真实持久化记录，不提供虚假的审核操作。
- 财务 Outbox 已持久化，但投递进程和消费者尚未完成。不得把 `order.paid` 待处理记录视为已经履约。

## 后续交付门槛

先完成报价、订单创建及实例金额写入，再接真实支付渠道、回调验签、Outbox 消费和渠道对账。售后阶段分别接入退款、发票和例外提现的审核与处置状态机；最后接服务实例自动续费。每增加一个写接口，都要补充对象归属、权限、幂等、并发和失败恢复测试。

真实数据库升级使用 `php webman system:migration-status` 检查并在备份后运行 `php webman system:migrate`。SQLite 迁移测试不能代替 MySQL 迁移、支付渠道联调和真实购买验证。

ORM、事务契约、服务首次订单关联及实测范围见 [现有系统与 ORM 重构实施说明](../architecture/current-system-refactor.md)。
