# 财务管理实施状态与使用说明

## 已实现的社区版功能

| 页面 | 功能 | 前端入口与服务端授权 |
| --- | --- | --- |
| 订单管理 | 创建购买订单、余额付款、取消未支付订单、备注、详情及退款/开票入口 | `admin.page.order-list.view/create/pay/cancel/update` |
| 充值记录 | 线下收款核实后入账、唯一收款凭证、自动生成支付交易、资金来源与余额流水 | `recharges.view/create` |
| 支付记录 | 只读交易列表与详情，不允许人工篡改第三方支付状态 | `payments.view` |
| 资金流水 | 只读入账、消费、退款、冻结、解冻及打款记录 | `transactions.view` |
| 退款记录 | 单实例申请、额度预留、审核通过/驳回、执行余额退款 | `refunds.view/create/review/execute` |
| 发票记录 | 净实付开票申请、实例金额归属、审核、真实开票号码登记、真实红字号码登记 | `invoices.view/create/review/issue/red` |
| 提现记录 | 指定充值来源申请、冻结、审核、驳回解冻、真实打款凭证登记 | `withdrawals.view/create/review/payout` |

六类财务页面的权限码以 `admin.finance.` 为前缀，订单权限保留 `admin.page.order-list.` 前缀。角色分配按财务菜单显示操作权限，创建、审核、执行分别授权；每个写接口同时要求查看权限。会员选择仅提供有创建权限的财务管理员必要的 ID 与昵称，不要求额外开放全部会员管理权限。

六类财务列表均使用独立字段查询，包含单号、会员 ID、时间及适用的状态；条件按 AND 组合，查询和重置回到第一页，已应用条件、排序和分页保存于 URL。查询与工具栏分开，右侧全局操作带图标，表格操作列使用文字链接。详情和操作使用单一 Drawer，不叠加抽屉。财务操作只展示真实数据库记录，空列表不自动切换为可操作的演示交易。

## 操作流程

### 线下充值

在充值记录右上点击「线下充值入账」，选择会员、填写金额、唯一收款凭证和选填备注。管理员须先核实真实收款；保存后生成 `offline` 支付记录并通过公开余额门面核对金额、币种、会员及渠道，写入充值来源批次和不可变流水。相同凭证不得重复入账。线上支付插件的创建交易、回调验签和对账不由线下入账入口代替。在线充值已接入两端及核心幂等入账，见[在线充值说明](online-payments.md)。

### 单实例退款

退款记录中选择会员后仅展示可处理的订单实例。实例须未关联已交付服务，或其服务已在业务管理终止；实际供应资源释放仍需由履约模块确认。当前仅执行已核实的余额支付订单退款，退回原消费的充值批次，不生成虚构充值收入，不影响同单其他实例。

申请金额上限为该实例实付分摊金额减去已退、退款预留及已占用开票金额。申请后预留额度；驳回释放；审核通过后独立执行，更新实例、订单退款汇总、会员余额、消费来源恢复值和退款流水。多实例与不同产品均使用 `order_item_units`，不在财务模块按云服务器类型分支。金额以交易创建时的分摊为准，不按当前商品价格重算历史优惠。

已开票部分须先完成实际红冲并登记，再退款。退款政策期限、供应资源释放确认、原支付渠道退款、渠道结果未知恢复及上游采购退款仍需后续产品/履约/支付用例接入；本轮不把手工金额录入解释成政策自动计算。

### 发票

申请选择已支付订单并填写抬头、发票类型和金额，按稳定实例 ID 顺序分配净实付额度。待审核、已通过及已开票单据均占用开票额度，驳回释放。登记开票要求实际发票号码；登记红冲要求实际红字发票号码，保留原发票及金额归属记录。页面只登记外部完成结果，不调用电子发票签发或税务红冲接口，不收集完整税务开票资料。

### 提现

社区版仅办理指定充值来源的未消费现金退还；不开放任意余额出金、返利提现或营销赠款提现。申请时同时扣减可用余额与来源剩余值，增加冻结余额，并写冻结流水；驳回恢复原来源和可用余额；审批通过后在外部完成打款，登记真实凭证并扣除冻结余额。打款流水的可用余额变动为零，因为申请时已经冻结扣减，避免重复扣减。

当前不存储或展示银行账号等收款敏感资料，也不提供自动打款。历史未核对的冻结或金额来源不能直接审批处置。

## 一致性与扩展边界

- 金额使用整数分，后台通过 `PriceInput` 以元输入；当前余额币种为 CNY。
- 创建和处置均带 `request_key`；同键同请求返回原单据，同键不同请求拒绝。浏览器网络失败重试保持同一键；改变内容时使用新键。
- `finance_operations` 的请求摘要、执行管理员、资源、动作与结果同业务事务提交，不保存密码、凭证报文或收款账户；常规后台操作日志另行记录成功/失败。
- 锁定与金额检查在服务端进行，选择区的可用额度仅为提示。固定锁顺序为订单、实例、账户、消费来源、产品库存；提现先锁充值，再锁账户及来源。并发首次入账、退款预留和提现冻结不得绕过这些边界。
- 订单写入通过 `OrderFinanceRepositoryInterface`，财务仓储不直接写订单表。只读跨模块业务来源查询显式选择安全字段，并批量预加载。
- 原订单的已付/退款金额和实例分摊共同约束退款；发票申请与退款共用订单锁，防止同时抢占同一额度。
- 资金流水不编辑、不删除；单据只能执行对应状态动作。金额归属不完整的历史发票阻止该订单新增退款与开票，旧单据只读保留，需独立迁移/核对方案。
- 退款完成持久化 `refund.completed` 财务 Outbox。当前仅写事件，不声明该事件已经投递、通知或完成上游采购退款。
- 财务按公共订单实例与资金来源建设，后续物理服务器、域名、证书和对象存储可以复用；活动和优惠券须在报价/订单时封存配置级优惠及实付分摊，不能在退款时追读当前营销规则。

## 数据库与运行

`20260927000200` 为原财务基础；新增 `20261008000200` 扩展单据创建人、备注、审核意见、线下凭证、红冲登记及幂等审计表，`20261008000300` 补齐财务审计标识的中文字段说明。仅使用前向迁移，不修改已执行的基础迁移。

执行前备份数据库，使用 `php webman system:migration-status` 核对待执行版本，再运行 `php webman system:migrate --force`。本轮新增控制器与容器绑定，需完整 restart；管理员重新登录刷新操作权限。

后台订单流程见 [订单管理说明](order-management.md)。新订单在单实例全额退款时通过产品库存契约释放占用，部分退款保留占用。

契约见 `contracts/openapi/admin-finance.v1.yaml`；订单详情新增可选 `units` 实例金额数组，保留原 `items` 与旧消费者兼容。

- `vendor/bin/phpunit tests/integration/FinanceWorkflowTest.php`：真实迁移上的独立 SQLite 数据库，覆盖幂等、重复凭证、单实例退款、退款驳回、原来源恢复、开票占用/红冲释放、冻结/解冻/打款、越权与异常回滚、真实 Controller 查询与写入；并发测试仅在 MySQL 执行。
- `HOWSTACK_MYSQL_TEST=1 vendor/bin/phpunit tests/integration/FinanceWorkflowTest.php`：创建并清理独立 MySQL 数据库；两个独立进程验证同键充值只入账一次、竞争提现不超余额。
- `frontend/admin/tests/finance-workflows-browser.mjs`：模拟 API 下验证桌面/390px、六类列表、操作权限、表单验证、整数分转换、审核与处置交互、组合查询/重置及页面溢出。模拟 API 不代表真实浏览器登录或支付/税务/银行联调。
- 支付插件真实回调、原渠道退款、税务签发、银行打款、生产资源释放以及生产数据验收分别保留外部验证边界。
