# 皓量云擎云业务运营系统前端开发规范

## 适用范围

本文件适用于 `frontend/` 及其所有子目录，并继承仓库根目录 `AGENTS.md`。子目录若存在更具体的 `AGENTS.md`，继续叠加执行。

## 技术栈与应用边界

- 三个应用使用 TypeScript 和 Vite；运营后台使用 React 18 与 Arco Design React，会员控制台使用 React 19 与 Ant Design 6，在线安装器使用 React 19 与 Arco Design React。
- `admin/` 是运营后台，`console/` 是会员控制台，`install/` 是在线安装器；三者必须保持独立构建和独立路由。
- 三个应用的生产构建统一输出到 `backend/public/` 的受控目录，随后端发行包交付；客户服务器不得依赖 Node.js 或现场构建。
- 禁止从一个应用直接引用另一个应用的 `src/`；需要复用的 API、类型、Schema 渲染器和通用组件应进入 `packages/`，并通过明确的包入口导入。
- 共享包必须有清晰职责和稳定公开 API，禁止把具体业务页面或应用私有状态迁入共享层。
- 禁止直接修改 `node_modules/`、`dist/` 及其他构建生成内容。

## TypeScript 与 React 规范

- 禁止使用 `any`；外部数据先定义类型，并在 API、存储、消息和插件边界完成运行时校验。
- 组件保持单一职责；业务请求、状态编排和展示逻辑应合理拆分，避免超大页面组件。
- Hooks 必须遵循调用规则，副作用需明确依赖和清理逻辑，不在渲染阶段执行写操作。
- API 地址、路由名称、权限标识、查询键和缓存策略集中管理，不在页面组件中散落硬编码。
- 页面必须处理加载、空数据、错误、无权限和提交中状态；异步操作应防止重复提交并提供清晰反馈。
- 用户可见文案默认使用中文；协议字段、产品标识和第三方专有名词按实际契约保留英文。

## 复用、工具与组件规范

- 多处重复且语义稳定的操作可以封装为工具函数、工具模块、Hook 或组件，避免复制粘贴；封装前应确认职责、输入输出、状态和副作用边界清晰，不能为单次使用或表面相似的代码过早抽象。
- 日期、金额、文本、枚举映射、脱敏、校验和序列化等无 UI、无状态的逻辑优先封装为纯工具函数；TypeScript 中优先使用具名函数和模块，仅在确需封装实例状态或明确协议时使用工具类。
- 包含 React 状态、副作用、请求编排或浏览器生命周期的可复用操作应封装为自定义 Hook，不得伪装成普通工具函数，也不得绕过 Hooks 调用规则。
- 可复用的视觉结构和交互行为应封装为组件；组件通过类型明确的 Props、事件和受控状态对外通信，不得隐藏依赖于页面全局变量、路由对象或未声明 Context 的行为。
- 业务规则、权限决策和完整业务流程不得塞入万能工具或通用组件。页面负责用例编排，领域相关逻辑放在对应业务模块；公共组件只承载稳定、可组合的展示与交互能力。
- 仅在单个应用内复用的代码放入该应用的 `src/` 对应目录；跨 `admin`、`console`、`install` 复用且契约稳定的工具、Hook、类型和组件才进入 `frontend/packages/`，禁止跨应用直接引用彼此源码。
- 不得创建职责含糊的 `utils.ts`、`common.ts` 或超大 `CommonComponent`；文件、导出名称和目录应表达具体用途，并保持可按需导入，避免循环依赖和无边界公共 API。
- 工具、Hook 和组件应覆盖空值、异常、加载、禁用及边界输入；导出的公共能力必须补充准确类型和 TSDoc，重要纯逻辑应有单元测试，交互组件应按风险补充组件或浏览器测试。
- 抽取或修改公共能力前必须搜索全部调用方，保持兼容或提供明确迁移；不得为了消除少量重复而引入更难理解的配置层或条件分支。

## 注释与 TSDoc 规范

- 对导出的组件、Hooks、函数、类型、接口、类、常量和共享包公共 API 尽量编写 TSDoc，说明用途、参数、返回值、状态变化、副作用、错误行为和使用约束。
- TSDoc 使用标准的 `/** ... */` 形式；根据实际需要准确使用 `@param`、`@returns`、`@throws`、`@remarks`、`@example`、`@typeParam`、`@deprecated` 和 `@see` 等标签。
- 组件 Props、Schema、API DTO、插件消息和复杂联合类型中的字段，如果名称不足以表达业务语义、单位、取值范围、可空条件或兼容规则，应逐项补充文档注释。
- TSDoc 不能替代 TypeScript 类型；应优先提供精确类型和判别联合，文档负责补充类型系统无法表达的业务语义、运行时校验要求与调用约定。
- Hooks 依赖、缓存失效、竞态处理、权限判断、跨窗口通信和兼容性分支等不直观逻辑，应使用行内注释解释设计原因，不要逐行复述代码或保留大段已注释掉的废弃实现。
- 注释必须与实现同步更新；公共 API 行为变更时同步更新 TSDoc、示例和弃用说明，过期或误导性注释必须修正或删除。

## ProComponents 组件选型规范

本节适用于会员控制台。运营后台遵循 `frontend/admin/AGENTS.md`；在线安装器使用轻量的 Arco Design React 原生组件，遵循 `frontend/install/AGENTS.md`。

- 会员控制台的业务页面默认优先使用 `@ant-design/pro-components` 已封装的组件能力，不重复组合 Ant Design 原子组件实现 ProComponents 已覆盖的查询、表格、表单、详情、列表、卡片和指标场景。
- 数据展示表格默认使用 `ProTable`，并优先通过 `columns`、`request`、`valueType`、`valueEnum`、`search`、`pagination`、`toolBarRender`、`tableAlertRender` 和 `actionRef` 等公开能力完成查询、展示、分页、批量操作和刷新。仅当表格是无查询、无分页、无工具栏、数据量很小的局部静态展示，或 `ProTable` 明显不适合该交互时，才使用 Ant Design `Table`，并在实现或审查说明中写明原因。
- 录入和配置页面优先使用 `ProForm` 体系；基础字段使用 `ProFormText`、`ProFormSelect` 等对应组件，复杂筛选优先 `QueryFilter`，多步骤流程优先 `StepsForm`。不得手写状态编排、提交栏和字段联动来重复实现 ProForm 已提供的能力。
- 只读详情优先使用 `ProDescriptions`，业务列表优先使用 `ProList`，业务内容容器优先使用 `ProCard`，核心指标优先使用 `StatisticCard`；组件选型必须匹配真实业务语义，不得仅为使用 ProComponents 而增加多余容器或嵌套层级。
- 页面框架在符合现有路由和布局方案时优先复用 `ProLayout`、`PageContainer` 等能力；已有自定义 Layout 能稳定满足需求时不得重复套入第二套页面框架、标题或面包屑。
- 使用 ProComponents 时必须遵循项目实际安装版本的公开 API 和类型定义，优先配置组件能力，不依赖私有 DOM、内部类名或样式覆盖；缺失能力先评估组合公开 Props、插槽和受控状态，再决定是否封装项目组件。
- Ant Design 原子组件仍用于按钮、提示、弹窗、抽屉、标签、排版及 ProComponents 内部自定义渲染。极轻量的局部静态展示可以使用 Ant Design 原生组件，不得仅为形式统一引入不必要的 ProComponents 依赖。

## Ant Design 与视觉规范

本节中的 Ant Design 组件、Token、图表及 `ant-design-skill` 规则适用于会员控制台；在线安装器对应规则见 `frontend/install/AGENTS.md`，运营后台对应规则见 `frontend/admin/AGENTS.md`。移动端与安全要求适用于所有应用。

- 优先使用 Ant Design 6、ProComponents 和项目已有组件，不重复实现已有基础组件。
- 全局主题色固定为 `#165DFF`，矩形组件全局圆角固定为 `2px`；头像、状态点和其他具有圆形语义的元素可以保持圆形。
- 主题令牌必须在应用根部通过 `ConfigProvider` 集中配置；业务组件使用 Design Token 或项目 CSS 变量，不散落同义色值和圆角硬编码。
- 本项目明确的 `2px` 圆角优先于通用组件模板的默认圆角；复制 Skill 模板后必须同步调整 Ant Design Token 和 CSS 变量。
- Ant Design 和 ProComponents 自带的视觉样式、交互状态与内部结构原则上直接使用，不做重复覆盖；除应用根部通过 `ConfigProvider` 设置的项目级全局 Token 外，禁止使用 `.ant-*` 内部类选择器、依赖组件私有 DOM 结构、`!important` 或私有 CSS 变量重写组件样式。需要调整行为或外观时，优先使用公开 Props、插槽和 Design Token。
- 项目自定义样式禁止主动增加阴影，包括 `box-shadow`、`text-shadow` 和 `filter: drop-shadow()`；层级使用实色背景、边框、间距和排版表达。Ant Design 组件自带的阴影与交互状态保持官方默认，不得仅为移除原生效果编写覆盖样式。
- 禁止在项目自定义样式中使用视觉悬浮效果，不得通过位移、缩放、悬停抬升或悬浮卡片表达状态；页面布局使用 Flex、Grid 或正常文档流，不使用 CSS `float`。Modal、Drawer、Dropdown、Popover 和 Tooltip 等功能性浮层直接使用 Ant Design 默认样式，不额外添加阴影、模糊或抬升动效。
- 禁止拟态玻璃效果，不使用 `backdrop-filter`、背景模糊、半透明玻璃面板、高光叠加或类似视觉处理。
- 禁止渐变色，不使用 `linear-gradient()`、`radial-gradient()`、`conic-gradient()`、渐变遮罩或渐变文字；背景、边框、图表和状态颜色均使用单一设计令牌色值。
- 禁止自定义圆角；矩形组件只能使用全局 `2px` 圆角 Token，不得在页面、组件、内联样式或局部 CSS 中另行硬编码其他圆角值；只有头像、状态点、圆形图标按钮等明确具有圆形语义的元素可使用 `50%`。
- 所有业务图表统一使用 `@ant-design/charts`，并遵循项目实际安装版本的官方 API；禁止引入 ECharts、Chart.js、Recharts，禁止手写 Canvas、SVG 或使用静态图片模拟图表。仅展示单个统计值时使用 Ant Design `Statistic` 或 ProComponents `StatisticCard`，涉及趋势、分布、占比或关系的数据可视化仍须使用 Ant Design Charts。
- 新建中后台布局、表格、列表、表单、详情或图表页面时，使用项目 `ant-design-skill` 中对应规范和模板起步；已有页面优先复用现有布局与视觉体系。
- 页面标题只由业务页面层提供；Layout 负责导航和内容容器，不重复自动渲染标题或面包屑。
- 表格和列表应设置稳定的列宽、溢出和空状态策略；操作区不得因中文文案换行、遮挡或被裁切。
- 所有页面从设计、开发到验收都必须考虑移动端自适应，不能只满足桌面端；至少验证桌面端与 `390px` 宽移动端，并检查导航、表单、表格、卡片、弹窗与抽屉的布局重排、可操作性、横向溢出、滚动归属及控制台错误。

## 插件前端边界

- 插件前端必须以预构建、版本化资源交付，客户服务器不执行 `npm install` 或运行时编译。
- 产品类型必须拥有与其业务语义匹配的专属管理页面和购买配置器。云服务器的地域、可用区、线路、规格、镜像、系统盘、数据盘、带宽、IP、防护和初始化信息等关键结构、联动与价格交互使用类型明确的组件和 DTO，不得用通用键值表单或一套万能 Schema 页面替代。
- 普通配置表单、附加字段和适合通用渲染的插件界面优先使用 Schema UI，由主应用控制组件白名单、运行时校验、权限和主题。Schema UI 不负责复杂产品的核心组合校验、敏感凭证输入处理或最终计价，服务端仍须完整校验。
- 前端调用产品类型提供的可选项解析、配置校验和报价接口；选择条件变化后清理失效值并展示不可选原因。前端计算只能用于即时预览，订单金额、供应绑定和购买资格以服务端报价为准。
- 报价、订单和服务页面必须显示其创建时的产品类型及销售版本语义，不能以当前商品配置重新解释历史快照。密码、私钥等敏感值使用专用输入和一次性提交，不进入浏览器持久存储、普通表格、日志或可回显 DTO。
- 小型页面扩展使用受控 Slot，明确可传入的数据、可触发的动作及生命周期。
- 插件界面统一使用受信的预构建扩展、公开 SDK 和受控页面/Slot 扩展点，不要求 iframe。SDK 明确可用数据、路由、权限、动作和主题接口，不依赖主应用私有 Context 或内部 API；同域 JavaScript 按受信代码审核，运行时加载另列后续建设。
- 插件资源加载必须校验清单、版本、权限、来源和完整性，并支持禁用、失败回退及缓存失效。

- 展示服务实例的 `status=active` 使用“已开通”，不解释为资源运行中；开关机状态由未来的生产能力单独提供。来源订单固定为首次交付订单，续费、升级等后续交易分别关联订单单位。

## 前端安全

- 不在源码、构建变量或浏览器持久存储中硬编码密钥、管理员令牌和生产凭据。
- 展示富文本、模板内容和插件消息时必须按信任边界进行转义、净化和来源校验。
- 权限控制不能只隐藏按钮；前端负责交互提示，最终鉴权与对象归属校验必须由后端完成。
- 上传前端需校验类型和大小并提供用户反馈，但不得把客户端校验视为服务端安全保证。

## 前端验证

运营后台常用检查：

```bash
cd admin
pnpm lint
pnpm build
```

会员控制台常用检查：

```bash
cd console
pnpm lint
pnpm build
```

在线安装器常用检查：

```bash
cd install
pnpm lint
pnpm build
```

- 修改共享包时，必须验证所有受影响的应用，而不是只验证共享包本身。
- 视觉或交互改动除 lint/build 外，还应通过浏览器检查目标页面、关键响应式尺寸、溢出、交互状态和控制台错误。
- 涉及路由、权限、请求缓存或插件加载时，覆盖直接访问、刷新、失败、无权限及禁用等边界场景。
